1. What is an eval?

An AI system gives different-looking answers every time, and "it seems to work when I try it" doesn't tell you whether a change made it better or worse. An eval fixes that by turning "seems good" into a number you can compare.

The recipe is always the same:

  1. Write a fixed list of questions where you already know the right answer.
  2. Run the system on all of them.
  3. Score each result against the known answer.
  4. Average the scores. Change something, run again, compare.
.NET analogy

An eval is a test suite with a score instead of green/red. A unit test says "this one case passes". An eval says "17 of 20 cases pass, and here is how early the right answer showed up". The labelled questions are your test fixtures. The scoring function is your assertion. The difference: AI systems are fuzzy, so you care about how often and how well it's right, not a single pass/fail.

2. What this project's eval measures (and doesn't)

This app answers regulatory questions using RAG (Retrieval-Augmented Generation). That's two stages:

  1. Retrieve: turn the question into an embedding (a list of numbers capturing its meaning) and find the stored document Chunks whose embeddings are closest.
  2. Generate: hand those Chunks to an LLM and ask it to write an answer.

The eval in /eval tests stage 1 only. The question it asks is:

"When someone asks this question, does the right passage come back near the top of the search results?"

No LLM writes an answer during the eval. Why test only the first half? Because if retrieval hands the LLM the wrong passages, nothing downstream can save it. And retrieval is cheap, fast and deterministic, so it makes a clean thing to measure first.

Concept: embeddings

Each Chunk was converted to a vector (here by the nomic-embed-text model) and stored in Postgres. A question is converted the same way, and the database returns the Chunks whose vectors point in the most similar direction (cosine similarity, 1 = same meaning). The eval doesn't test the maths. It tests whether the results are useful.

3. The whole thing in one picture

Everything lives in run_eval.py. Running it does this:

1. Load dataset.json: 20 hand-written questions, each labelled with where the answer lives.
▼
2. Embed each question (with the prefix "search_query: ") using the local Ollama model.
▼
3. Retrieve the top 10 nearest Chunks from Postgres (one SQL query).
▼
4. Score each case: is any of the 10 a hit? At which rank? (match.py)
▼
5. Summarise into Recall@1/3/5/10 and MRR, overall and split by question type.
▼
6. Save a report to eval/runs/<timestamp>-<model>.json. Never overwritten.

The three ideas that matter are: the questions (step 1), what counts as a hit (step 4), and how hits become numbers (step 5). The next three sections take them in turn.

4. Part 1: the Eval Cases (the questions)

Each case in dataset.json looks like this (shortened):

{
  "id": "q01",
  "question": "What is a disadvantage related to mortgage incentives?",
  "phrasing": "lexical",
  "category": "single_passage",
  "gold_locators": [
    { "document_id": "doc-09-cp158-consumer-protection-code",
      "locator": "Mortgage Incentives (p. 44)" }
  ],
  "answer_quote": "One clear drawback regarding mortgage incentives is that..."
}

Gold Locators: the "right answer" label

A Gold Locator says where in the source the answer lives: a document plus a section reference (a clause number like 3.12, or a heading plus page like Mortgage Incentives (p. 44)).

Notice it is not a Chunk ID. Chunks are immutable: re-chunk a document and every Chunk gets a new ID. If the labels pointed at Chunk IDs, you'd have to re-label the whole eval set every time you improved the chunker. A locator comes from the document's own structure, so it survives re-chunking. This means you can compare two chunkers on the same questions. (ADR-0027)

The answer_quote is only a human sanity check. It's never used for matching.

Two tags on every question

TagValuesWhy it exists
phrasinglexical / paraphrase Lexical questions reuse the passage's own words. Paraphrases deliberately avoid them, the way a real user who has never read the document would ask. About half of each.
categorysingle_passage, multi_locator, supersession, unanswerable Different shapes of question: one answer spot, answers spread over several spots, a newer document replacing an older one, and questions the corpus cannot answer.
Concept: lexical overlap bias

If you write a question while staring at a passage, you'll echo its wording. Retrieval then finds it easily, and your score looks great, but real users don't know the document's wording. Rather than pretend the bias isn't there, the project tags it and measures it: the gap between lexical and paraphrase scores tells you how much the system understands meaning versus matching words. (ADR-0029)

The questions are hand-written by you, not generated by an LLM. LLM-drafted questions echo source wording even more, and the set would stop reflecting your judgement of what matters.

Unanswerable cases (e.g. "What is the US FDIC deposit insurance limit?", which isn't in the Irish regulatory corpus) have no Gold Locators. They are not scored for recall, because there is nothing to find. They exist for a different purpose, explained in section 6.

5. Part 2: deciding if a result is a hit

For each question, retrieval returns 10 Chunks, each with a document ID and locator. A Chunk is a hit if its locator matches a Gold Locator in the same document. That sounds trivial, but "match" needs care. The rule lives in match.py (ADR-0028).

Clause numbers: compare segments, not text

Gold 3.1 must not be satisfied by retrieved 3.12. A naive "3.12".startswith("3.1") says yes, which would be a false hit. So the locator is split into segments (["3","1"] vs ["3","12"]) and the gold's segments must be a prefix of the retrieved ones.

GoldRetrievedHit?Why
3.123.12yesidentical
3.123.12(a)yesa child of the gold clause
3.13.12no"1" ≠ "12" as whole segments

Heading + page: exact heading, page within ±1

For documents without clause numbers, the heading must match exactly, and the page may differ by at most one. The page is kept because it distinguishes repeated headings like "Introduction", and the ±1 tolerance absorbs a chunker that paginates slightly differently.

The rule is deliberately dumb

Design principle: a deterministic grader

The match rule is plain code: no fuzzy matching, no similarity, no LLM judge. The eval is measuring the retriever. If the grader itself were noisy (as an LLM judge would be), you couldn't tell whether a score changed because retrieval improved or because the grader wobbled. One thing varies at a time.

And if the rule can't understand a locator, it raises an error instead of returning "no match". A silent "no match" would be counted as a retrieval failure, producing a plausible but wrong number. A loud crash is better than a quiet lie. The harness does the same if the database has no embeddings: it stops rather than scoring every question a miss.

6. Part 3: turning hits into numbers

For each answerable case, the harness records one thing: the rank of the first hit (1 = top result), or "none" if nothing in the top 10 was a hit. Everything else is arithmetic on those ranks.

Recall@k: "was it in the top k?"

Recall@3 = the fraction of questions whose first correct Chunk appeared in the top 3. Simple and readable. Why does k matter? Because the LLM in stage 2 is only handed the top few Chunks (Track B's default is 5). A right answer at rank 9 is as good as missing.

MRR: "how high was it?"

Recall@k can't tell rank 1 from rank 3. Mean Reciprocal Rank scores each case as 1 / rank (rank 1 = 1.0, rank 2 = 0.5, rank 4 = 0.25, a miss = 0) and averages them. It rewards putting the right Chunk first.

Worked example

Three questions. The first hit lands at rank 1, rank 2, and never:

CaseFirst hit rankin top 1?in top 3?1/rank
A1✓✓1.00
B2✗✓0.50
Cnone✗✗0.00
ResultRecall@1 = 1/3Recall@3 = 2/3MRR = 1.5/3 = 0.50

Where do unanswerable questions fit?

They're left out of every metric (there's no right Chunk, so "recall" is meaningless). Vector search always returns the 10 nearest Chunks, even for a nonsense question; it never says "nothing found". So for these cases the harness records the top-1 similarity score instead: how confident the best wrong match looked. Later, if answerable questions score clearly higher than unanswerable ones, you could set a threshold ("below 0.75, say we don't know"). If the two overlap heavily, that's a finding too. (ADR-0029/0030)

How to read it

  • Overall Recall@1 = 0.67: for 12 of the 18 questions, the very top result was correct. By rank 5, 16 of 18 were found. Two questions (q06, q08, both paraphrases) never surfaced in the top 10.
  • The big finding is the phrasing gap. Lexical Recall@1 is 0.89; paraphrase is 0.44. When the question reuses the document's words, retrieval is excellent. When it's asked the way a real person would ask, it roughly halves. That is exactly the lexical-overlap bias the tags were designed to expose, and it's the main reason to try improvements such as hybrid (keyword + vector) search.
  • Small numbers. With 2 to 3 cases per category, one question flipping changes a row by 33 to 50 points. Treat the by-category rows as hints, not conclusions. The overall and by-phrasing rows (9 each) are more trustworthy.
  • Unanswerable: the two cases had top-1 similarities of 0.727 and 0.705. The weakest correct hit was 0.652, so the scores overlap, and a simple threshold would not cleanly separate the two groups with this model. Thin data (2 cases), but an early finding.

8. Why every run is saved and never overwritten

A score means nothing without knowing what produced it. Change the embedding model, how a document was chunked, the question set, or k, and the number moves. So each run writes a new JSON file recording:

  • Config: embedding model, query prefix, k, dataset_version, and every document's active chunking generation.
  • Summary: the table above.
  • One line per case: its hit rank and similarity scores, plus the full top-10 retrieved, so a miss is investigable ("why did q06 not appear?").

Files are opened in mode "x", which fails if the file already exists, so history can't be overwritten. Two reports are only compared when their configs match, like-for-like. (ADR-0030)

Event sourcing analogy

Run reports are append-only, like your event store: you never edit a past run, you add a new one beside it. The harness even reads the database in a REPEATABLE READ, read-only transaction so every search in one run sees the same frozen snapshot.

9. Where else the eval is used

The first report is the baseline: the score any later retriever must reproduce on identical data. Track B's LangChain retriever reuses the same SQL and the same match.py rule, and the opt-in test track-b/tests/test_baseline_parity.py runs every answerable case through it and checks recall equals the baseline. If Python and .NET scored differently on the same embeddings, that would point to a porting bug (a missing query prefix, wrong distance operator), not the model. So the eval doubles as a regression test for the port.

10. What is not evaluated yet

  • Answer quality. Nothing yet checks whether the LLM's drafted answer is correct or faithful to the Chunks. This eval stops at retrieval.
  • The verify judge. Track B's verify step uses an LLM to mark each claim in an answer as supported or unsupported and computes a Confidence score (ADR-0035). The source notes that its 0.8 threshold is "a first guess, to be revisited once verify has evals". So the judge itself has no eval yet, and that's a natural next step (compare its verdicts against human labels).
  • Hybrid search. Planned as a separate, measured change: you'd run the same eval before and after and compare reports.

11. Try it yourself

Test 1 (no dependencies): the match rule

eval/tests/test_match.py::test_clause_does_not_match_a_different_clause

python -m pytest eval/tests/test_match.py::test_clause_does_not_match_a_different_clause -v

Shows: the "3.1 is not 3.12" rule from section 5, the single most instructive piece of the grader.
Poke at it: open match.py and change _clause_covers to return ".".join(retrieved_segments).startswith(".".join(gold_segments)). Rerun and watch it fail. That's the naive bug the rule exists to prevent.
Why this one: it needs nothing running and shows the rule's reason for existing in one failing case.

Test 2 (needs Postgres, not Ollama): the metrics

eval/tests/test_run_eval.py::test_recall_and_mrr_over_answerable_cases_only

python -m pytest eval/tests/test_run_eval.py::test_recall_and_mrr_over_answerable_cases_only -v

Shows: hand-built vectors and a fake embedder produce predictable ranks, and the test checks Recall@k and MRR come out as the arithmetic in section 6 says, with unanswerable cases excluded.
Poke at it: print the report["summary"]["overall"] inside the test, or change a fixture vector so a case ranks differently and watch MRR move.
Why this one: it is the clearest end-to-end illustration of ranks becoming numbers. It skips itself if the test Postgres container isn't up (docker compose up -d in store/).

See a real report

Open eval/runs/20260929T111257Z-nomic-embed-text.json and look at case q06: hit_rank is null, and its retrieved list shows what came back instead. That is how you debug a miss. To run the real thing: python -m regdocs_eval.run_eval (needs Postgres loaded and embedded, plus Ollama).

Summary

The project's eval measures one thing: given a hand-written question, does retrieval put the right passage near the top? Each question is labelled with a Gold Locator (a stable document-structure reference, not a Chunk ID). A deterministic, structure-aware rule decides hits. The first hit's rank becomes Recall@k and MRR, broken down by lexical vs paraphrase phrasing and by question category. Every run is saved as an immutable report pinning its configuration, so numbers are only compared like-for-like. The baseline shows strong results on lexical questions and a big drop on paraphrases, which is the evidence for the next improvement. Answer quality and the verify judge have no evals yet.
