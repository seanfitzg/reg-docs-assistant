Issue #30 — The Gold Locator match rule

The grader for the retrieval eval: a small, pure function that decides whether a retrieved Chunk counts as a hit for a Gold Locator. No model and no fuzziness, just rules. It was built test-first, and review turned up a comment that explained the core bug backwards and a place where bad data could still hide as a "miss". Follows issue #29's writeup.

Where this fits

#29 schema + checks + helper → #31 you write the cases → #32 harness + baseline ← #30 match rule

#29 left the eval set with labels: every Eval Case names where its answer lives as a Gold Locator, (document_id, locator). #32 will run retrieval and get back a ranked list of Chunks, each with its own (document_id, locator). Something has to compare the two and say hit or miss. That's this ticket: eval/match.py, with two public functions, locator_matches() and case_hit(). It's covered by 51 unit tests in eval/tests/test_match.py, and every one of the 1,993 real active locators was checked against it.

The concepts

Concept: the grader must be deterministic (ADR-0028)

An eval produces a number such as "Recall@5 = 0.72", and its whole value is that you can compare that number before and after a change. If the grader had its own variance (an LLM judge that says "hit" 9 times out of 10, or a fuzzy string similarity with a threshold), then a score moving from 0.72 to 0.68 could be the retriever getting worse or the grader wobbling. You couldn't tell which. That's the same reason a flaky test is worse than no test.

This is why many AI evals put so much effort into their grading method. LLM-as-judge is common for grading free-text answers, because there's no exact right string. Here we're grading retrieval, where the right answer is a place in a document, so a hand-written rule can do it exactly and for free. Use the cheapest deterministic grader that works, and save model judges for the problems that really need them.

Concept: why not just compare the strings?

Exact equality (gold == retrieved) would be correct for today's chunkers, but one of the eval's jobs is comparing chunkers (ADR-0027). Suppose a finer chunker splits clause 3.12 into 3.12(a) and 3.12(b). It retrieves 3.12(a), which is the right text. Exact equality scores that as a miss, so the finer chunker looks worse than it is. So the rule has to understand the structure of a locator:

StrategyLocator shapeRule
clause_numbered3.12, 3.12(a)The gold's segments must be a prefix of the retrieved's. A child clause is inside its parent.
heading_sections, academic_sectionsIntroduction (p. 3)The heading must match exactly, and the page may differ by at most ±1.

academic_sections shares the heading rule because its chunker builds locators the same way: f"{' '.join(lines)} (p. {page})" in ingestion/strategies/academic_sections.py. That was checked against the code and the data, not assumed (see below).

Concept: the startswith trap, and segments

The obvious way to say "3.12(a) is inside 3.12" is retrieved.startswith(gold). But "3.12".startswith("3.1") is True, so gold 3.1 would count 3.12 as a hit, and 3.10 through 3.19 as well. A string prefix is not a clause prefix. The fix is to split each locator into segments first and compare whole segments:

"3.12(a)"  →  ["3", "12", "(a)"]
"3.1"      →  ["3", "1"]

gold ["3","12"]  vs retrieved ["3","12","(a)"]   → first 2 equal      → HIT
gold ["3","1"]   vs retrieved ["3","12"]         → "1" != "12"        → miss
gold ["3","12","(a)"] vs retrieved ["3","12"]    → retrieved too short → miss

It's the difference between comparing file paths as strings ("/src/app".StartsWith("/src/a")) and comparing path segments. Most .NET developers have hit that bug with paths at some point, and it's the same bug here.

Concept: grader error goes both ways (the ±1 page tolerance)

A grader can be wrong in two directions. A false hit credits retrieval for something it didn't find, which inflates the score. A false miss blames retrieval for grader strictness, which deflates it. The ±1 page tolerance trades between them. It forgives a chunker that paginates slightly differently (fewer false misses). The cost is that two different sections with the same heading on neighbouring pages now count as the same place (a few false hits). The real corpus has exactly 4 such pairs. ±1 is ADR-0028's decision, and PAGE_TOLERANCE is a named constant so the decision is visible in the code.

Concept: fail loudly, never score a silent miss

The worst thing an eval can produce is a number that is wrong but plausible. Nobody questions a recall of 0.68. So when the rule meets something it doesn't understand (an unknown chunking strategy, or a locator that doesn't fit the expected format), it raises an exception instead of returning False. A False would be counted as a retrieval miss, and the bug would disappear into the average. It's the same instinct as preferring an exception over a swallowed catch {} in a batch job: a crash gets looked at, and a quietly wrong total doesn't.

What was built: eval/match.py

Each strategy is a pair of functions: parse turns a locator string into something comparable (and raises if it can't), and covers compares a parsed gold with a parsed retrieved locator. A dict maps strategy names to those pairs. It's the Python everyday equivalent of a Dictionary<string, (Func, Func)>, or a strategy-pattern lookup:

RULES = {
    "clause_numbered":   (_clause_segments, _clause_covers),
    "heading_sections":  (_parse_heading,   _heading_covers),
    "academic_sections": (_parse_heading,   _heading_covers),
}

def locator_matches(gold_locator, retrieved_locator, chunking_strategy) -> bool:
    parse, covers = _rule(chunking_strategy)            # raises on an unknown strategy
    return covers(parse(gold_locator), parse(retrieved_locator))

The parsers are two regular expressions, always applied with fullmatch, so the whole string must fit (like \A…\z in .NET). Otherwise "3.12." would slip through on its "3.12" prefix:

CLAUSE_PATTERN  = r"[0-9]+(?:\.[0-9]+)*(?:\([A-Za-z0-9]+\))*"   # 3, 3.12, 3.12(a), 3.12(a)(i)
HEADING_PATTERN = r"(.+) \(p\. ([0-9]+)\)"                         # "<heading> (p. <n>)"

case_hit() is what the harness will call once per Eval Case. It first checks every retrieved Chunk, then asks whether any gold matches any retrieved Chunk in the same Document:

def case_hit(gold_locators, retrieved) -> bool:
    for chunk in retrieved:                                  # every Chunk must be well-formed,
        parse, _ = _rule(chunk["chunking_strategy"])         # whatever Document it's from
        parse(chunk["locator"])

    return any(
        locator_matches(gold["locator"], chunk["locator"], chunk["chunking_strategy"])
        for gold in gold_locators
        for chunk in retrieved
        if gold["document_id"] == chunk["document_id"]      # "1.1" exists in many Documents
    )

The same-Document filter matters because 1.1 appears in lots of Documents, and only the gold's own Document counts. "Any gold" is ADR-0028's rule for multi_locator cases: the answer lives in several places, and finding one is enough. An empty gold_locators (an unanswerable case) is never a hit, because any() over nothing is False. The harness excludes those cases from recall anyway (ADR-0029).

How it was built: red, green, then review

Concept: TDD against a pure function

A pure function (no I/O, same inputs → same output) is the easiest thing to test-drive, which is why the issue asked for this one test-first. All the tests were written before match.py existed. The first run failed with ModuleNotFoundError: No module named 'match', the red step. That's the Python equivalent of a test project that doesn't compile yet because the class doesn't exist. Then the implementation was written to make them green. During review, each fix again started with a failing test.

Checking the real data first

Before writing a rule, it's worth finding out what the locators actually look like, rather than trusting the ADR's examples. A quick script loaded every active Chunk, looked up its Document's strategy in ingestion/manifest.json, and tried each proposed pattern:

== clause_numbered 602          ← all fit N.N
== heading_sections 1242        ← all fit "<heading> (p. N)"; some odd ones:
     'Solvency  II - Implementation (p. 24)'     (a doubled space from PDF extraction)
     '(4) (p. 33)'                               (a heading that is itself in brackets)
== academic_sections 149        ← all fit "<heading> (p. N)"

Those odd locators became test cases. The doubled space is a good example of a decision the tests now pin: exact means exact. Both sides come from the same Document's extraction, so normalising whitespace would only risk merging two headings that really are different. After the implementation, the same script confirmed that every real locator parses and matches itself (1993 real locators hit themselves).

What /code-review caught

Two reviewers ran in parallel, one checking the repo's standards and one checking the spec (issue #30). Their findings, and what changed:

Bug: the core comment explained the bug backwards

The comment on _clause_covers said the segment rule was the difference from "a naive gold.startswith(retrieved)". That's the wrong way round. "3.1".startswith("3.12") is False, so the version as written wouldn't even show the bug. The trap is retrieved.startswith(gold). In this repo the comments are teaching material, so a wrong explanation of the central idea is a real defect, not a cosmetic one. It now spells out the example: "3.12".startswith("3.1") is True, so 3.12 would wrongly be scored as a hit for gold 3.1.

Bug: a true behaviour, credited to the wrong mechanism, "tested" by a case that couldn't fail

The first version said the page is always the last (p. N) "because .+ is greedy". The behaviour was right, but not for that reason. fullmatch pins (p. N) to the end of the string, so even a lazy .+? would land on the last one. The anchor does the work, not the greediness. The test meant to prove it used (4) (p. 33), and (4) doesn't look like (p. N) at all, so that case would pass under any reading. It now has a companion that could genuinely fail if the parser picked the first page: Notes (p. 2) (p. 33) vs Notes (p. 2) (p. 34) is a hit. The lesson generalises: before trusting a test as evidence, ask whether it could have failed.

Bug: bad data could still become a silent miss (a design change)

The spec says an unknown strategy or an unparseable locator "raises rather than silently returning False". locator_matches did raise. But case_hit only called it for pairs in the same Document. A retrieved Chunk from another Document with a bogus strategy was never looked at, and the case quietly scored a miss, which is exactly what the fail-loud principle forbids. The spec reviewer found this by trying inputs until one broke it:

case_hit([{"document_id": "A", "locator": "1.1"}],
         [{"document_id": "B", "locator": "Intro (p. 3)", "chunking_strategy": "bogus"}])
# first version: False       now: ValueError: unknown chunking strategy: 'bogus'

Fixing it changed the design. Originally each strategy mapped to a single matches(gold, retrieved) function, which parsed and compared in one step. That made it impossible to check a Chunk without comparing it to something. Splitting each rule into parse and covers lets case_hit parse every retrieved Chunk up front. It's a small example of a test pushing a design toward separate responsibilities.

One gap remains, and it's structural: a gold locator is only parsed when a Chunk from its Document is retrieved, because that's where its strategy comes from. That gap is already covered elsewhere. test_dataset.py (#29) checks that every gold exists exactly among the real Chunks, so any gold that passes is parseable by construction. The docstring says so.

Bug: \d means more than 0–9 in Python

In Python 3, \d matches any Unicode decimal digit, and int() converts them. So "X (p. ٣)" (an Arabic-Indic three) parsed as page 3, and "٣.12" passed as a clause. That's harmless with this corpus, but "exact" should mean exact. The patterns now use [0-9], and two tests pin it. .NET has the same trap: \d is Unicode-aware there too unless you pass RegexOptions.ECMAScript.

Smaller fixes
  • The regex breakdown comment showed escaped spaces (\ \(p\.\ ) that the real pattern doesn't have.
  • The "like ^…$ in C#" analogy became \A…\z, because .NET's $ also matches just before a trailing newline.
  • pytest.raises (≈ Assert.Throws<T>), with (≈ using), {x!r} and dict.get() got explanatory comments.
  • The two error messages now both name strategies (clause_numbered, heading_sections/academic_sections).
  • The README's bullet had restated the whole rule, making a third copy next to ADR-0028 and the module header. It now points to the ADR instead.
Judgement calls left as they are

Plain dicts, not a GoldLocator type. The standards reviewer flagged Primitive Obsession: document_id + locator travel together as string-keyed dicts. That's fair, but dataset.json loads as dicts and check_dataset.py uses dicts, and #32's SQL rows will decide the natural shape. So the type is deferred to #32 rather than guessed at now.

case_hit returns a bool, not a rank. #32 needs "the 1-based rank of the first hit", and the spec asked for a bool here. The harness can call case_hit(gold, [chunk]) for each result in rank order and take the first True. If that turns out clumsy, a first_hit_rank() belongs in #32, when there's a real caller to design it against.

Something the data showed: locators aren't always unique

While trying to break the rule, the spec reviewer noticed that some locators appear on more than one Chunk in the same Document. That was verified against the data:

DocumentRepeated locatorsExample
CP08 (administrative sanctions)383.1 ×6, 3.3 ×6, 3.4 ×5
CP131 (recovery planning)72.1 ×2 … 4.1 ×2
Annual Report 20257Applications (p. 40) ×2
CP54, CP01, CP148, DP71–3 each3.57 ×2

This isn't a bug in the match rule. It's a fact about the corpus: CP08 restarts its clause numbering (or quotes other documents' numbering), and the chunker can't tell those apart. For #31 it means a gold of CP08 3.1 is ambiguous: retrieving any of the six 3.1 Chunks scores a hit, even ones about something else. That would inflate the score. When labelling, prefer passages whose locator is unique in its Document, or add a notes entry when you can't. The ±1 page tolerance adds 4 more near-collisions of the same kind (e.g. DP7's far include: (p. 62) vs (p. 63)). Several of those, like L (p. 13) and 351,648 (p. 166), are heading-detection noise that also showed up in #29.

What's next

#31 (writing the cases) and this ticket were the two blockers on #32. Once your cases are in, #32 embeds each question, runs a top-10 pgvector search, scores each case with case_hit, and writes the first baseline report. That's the first real number for how good retrieval is. When you write cases, keep the table above in mind: an ambiguous locator makes a case easier than it looks.
