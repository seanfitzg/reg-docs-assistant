Issue #44 — A permanent record that can't be edited, and the code that writes to it

Every answer the assistant gives is recorded as an "Event". This issue builds the place those Events live: a database table that only ever accepts new rows, plus a small writer that checks each Event is well-formed before saving it. Follows issue #43's writeup.

What the project is, and where we were

RegDocs Assistant answers questions about regulatory documents. Each time it answers, it should leave behind a record of what was asked, what it said, which source text it used and which warning flags it raised. That record is an Event. Until now an Event was only a Python dictionary returned by answer_question: validated against a JSON Schema in tests, then thrown away. Nothing was stored anywhere. Issue #43 had already made sure that dictionary holds placeholders like [REDACTED:EMAIL] instead of real personal data.

The problem, and the core idea

An audit trail is only trustworthy if nobody can quietly change it. If someone can edit an old Event, the trail proves nothing. The usual answer is "we agree not to edit rows". That holds until one buggy query, or one hand-typed UPDATE in a console, breaks it silently.

The idea here: make the database itself refuse. A trigger runs before any UPDATE or DELETE on the table and raises an error. A correction is not an edit; it is a new Event that points at the old one (ADR-0001).

Concept: append-only log (event sourcing, again)

You know this from event sourcing: state is a sequence of facts that are only ever appended, and history is never rewritten. The events table is the same thing, with the guarantee moved out of application discipline and into the storage engine. In .NET terms, think of an event store with no Update or Delete operation. Postgres allows both by default, so we had to add a trigger that takes them away.

Concept: why Redaction had to come first

Because the table is immutable, a leaked email address could never be removed once written. That is why issue #43 (Redaction) was built before this one. The writer relies on being handed an Event that answer_question already redacted. It deliberately does not scan the answer for PII itself: ADR-0034 explains that scanning answers would wrongly redact public text quoted from source documents, such as a regulator's contact email.

What the code now does

The table (store/init/004_events.sql)

events
  id           TEXT PRIMARY KEY           -- the Event's own id
  event_type   TEXT                       -- QueryAnswered / EventFlagged / AnswerOverridden
  recorded_at  TIMESTAMPTZ DEFAULT now()  -- stamped by the database
  payload      JSONB                      -- the full Event

recorded_at comes from the database's clock because the Event has no timestamp field, and a database clock can't be skewed or forged by the application. payload is JSONB because the three Event types have different shapes (ADR-0031); event_type is a real column so "show me every override" needs no JSON digging.

The trigger is a tiny function that raises events is append-only: UPDATE is not allowed (or DELETE). One honest limit: row triggers don't fire on TRUNCATE, so wiping the whole table remains a deliberate, privileged act. The tests use that to clean up regdocs_test.

Like the previous migration, the file applies itself to both regdocs and regdocs_test using a psql variable guard. Existing containers need it applied by hand (the store README gives the command).

The writer (track-b/src/regdocs_track_b/events.py)

write_event(event, db_url)
  1. look up the schema for event["event_type"]  (unknown type -> ValueError)
  2. validate the Event against it               (invalid -> ValidationError)
  3. INSERT id, event_type, payload              (database stamps recorded_at)

Validation runs before the database connection is even opened, so a bad Event writes nothing. The database doesn't re-check the payload's shape; that is the application's job (ADR-0031).

Example

Input: answer_question(graph, "My email is jane@x.ie, how much notice?"). The returned Event has query My email is [REDACTED:EMAIL], how much notice?. After write_event(event, DB_URL), the stored row's query is exactly that string, and jane@x.ie appears nowhere in the row.

Try it yourself

Needs the Postgres container running (docker compose up -d in /store, with migration 004 applied). Neither test needs Ollama.

1. The idea in one test: test_delete_on_events_is_rejected in store/tests/test_events_table.py.

python -m pytest store/tests/test_events_table.py::test_delete_on_events_is_rejected

It inserts a row, tries a raw SQL DELETE, and checks both that Postgres raised the error and that the row is still there. To see why it matters, drop the trigger in regdocs_test (DROP TRIGGER events_are_immutable ON events;) and rerun: the test fails because the delete succeeds. Restore it by re-running the trigger statement from 004_events.sql in that database.

2. The end-to-end one: test_a_pipeline_event_is_stored_with_redacted_query_and_answer in track-b/tests/test_events.py.

python -m pytest track-b/tests/test_events.py::test_a_pipeline_event_is_stored_with_redacted_query_and_answer

It runs a whole fake pipeline with an email in the question, writes the Event, reads the row back and checks the stored text. Add print(payload) before the asserts and run with -s to see what is actually persisted. Change the question to contain no PII and watch the placeholders disappear.

These two were chosen because between them they cover the two promises: the database refuses edits, and what gets stored is already redacted. The other tests (schema rejection, unknown type, each Event type) are variations on the writer's validation step.

Summary. Events now have a permanent home: an events table whose trigger makes Postgres itself refuse any UPDATE or DELETE, with the database stamping when each row was recorded. A small writer validates each Event against its JSON Schema before inserting, so malformed Events never land. Redaction stays where issue #43 put it, upstream in answer_question, so what the writer receives and stores already has placeholders instead of personal data.
