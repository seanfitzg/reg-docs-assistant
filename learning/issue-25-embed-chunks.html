Issue #25 — Embedding Chunks with a local Ollama model

The first genuinely AI-specific piece of /store: turning each Chunk's text into a vector, so a later ticket can search by meaning. A sequel to issue #19's writeup.

Where this fits

chunks (Postgres) → embed.py (this ticket) chunk_embeddings → (later) nearest-neighbour retrieval

store/embed.py reads every Chunk that belongs to its Document's active Chunking Generation, asks a local model (Ollama running nomic-embed-text) for a 768-number vector per Chunk, and stores it in a new chunk_embeddings table. It does no searching — that's the next ticket. Verified by 4 new integration tests plus the 6 existing loader tests, all green against the real Postgres (10 passed). One honest gap: Ollama isn't installed on the machine this was built on, so the real OllamaEmbeddingClient was never run against a live model; only its import and the response shape it indexes were checked. Try python store/embed.py yourself after ollama pull nomic-embed-text.

The concepts

Concept: what an embedding is

An embedding model is a neural network that maps text to a fixed-length list of numbers (here 768 floats). It's trained so that texts with similar meaning get vectors that point in similar directions — "capital requirements for banks" lands near "minimum own funds for credit institutions" even though they share almost no words. Retrieval then embeds the user's question the same way and asks the database for the stored vectors nearest to it. That's semantic search, as opposed to the keyword matching you'd get from SQL LIKE or full-text search.

Analogy, with limits: it's a hash function whose "collisions" are deliberate — similar inputs are meant to land close together. Unlike a hash, though, the output isn't comparable across models: vectors from two different models live in unrelated spaces. That's why the model name is part of the table's key (ADR-0024).

Concept: the asymmetric prefix (ADR-0026)

nomic-embed-text was trained with two roles in mind: text being stored is embedded as "search_document: " + text, and a query as "search_query: " + text. The model learned to place the two roles so questions land near the passages that answer them. Skip the prefix and nothing errors — retrieval just gets quietly worse, which is the nastiest kind of bug. So there's a test asserting the exact string the client receives, and chunks.text stays raw (the prefix exists only for the instant of the call).

Concept: pgvector's vector(768)

A column type from the pgvector extension (enabled back in #18). The 768 is enforced by Postgres: inserting a vector of any other length fails. Like decimal(18,2), the size is part of the type, so a model with different dimensions needs a different column — a future decision, deliberately not built now. There's no similarity index (hnsw/ivfflat) yet: those need tuning against real queries, which don't exist until retrieval does.

Concept: an injectable client, and Python's structural typing

embed_chunks(db_url, client) takes any object with an embed(text) -> list[float] method. The real script passes an Ollama-backed one; tests pass a tiny fake that records what it was asked. In C# you'd write an IEmbeddingClient interface and a mock. Python's typing.Protocol is the same idea but structural: a class counts as an EmbeddingClient just by having the method — it never declares "implements". That's why the test fake needs no shared base class and no mocking library. The payoff is the usual one for a seam: the test suite needs no Ollama, no network, no 270 MB model.

The core of embed.py is one query and one loop:

SELECT chunks.id, chunks.text
FROM chunks
JOIN documents
  ON chunks.document_id = documents.id
 AND chunks.chunking_generation_id = documents.active_chunking_generation_id   -- ADR-0025
LEFT JOIN chunk_embeddings
  ON chunk_embeddings.chunk_id = chunks.id AND chunk_embeddings.embedding_model = %(model)s
WHERE chunk_embeddings.chunk_id IS NULL                                        -- not embedded yet

for chunk_id, text in pending:

Where the spec needed more than it said

Four places where following the ticket literally would have failed or quietly misbehaved. All four were spotted while building, before review:

1. "Reuse the shared upsert helper" — but it couldn't

The ticket says to reuse db.upsert_immutable "with ON CONFLICT (chunk_id, embedding_model)". The helper (extracted in #24) hard-coded ON CONFLICT (id), and chunk_embeddings has no id column — the first insert would have been a SQL error. Fix: an optional conflict_columns parameter defaulting to ["id"], so every existing caller is unchanged. This is the payoff of doing #24 first: the change was one parameter in one shared place instead of a second copy of the upsert.

2. "ON CONFLICT DO NOTHING" does not mean "never recompute"

The ticket wants a re-run to never recompute an existing embedding. The upsert alone only prevents overwriting: every re-run would still ask Ollama to embed all ~2000 Chunks, then discard the answers, because the expensive model call happens before the insert. So the SELECT above excludes already-embedded Chunks (a SQL anti-join — LEFT JOIN ... WHERE right.key IS NULL, the set-difference cousin of LINQ's Except), and the upsert stays as a backstop. A test proves a second run makes zero client calls.

3. One transaction would have thrown away all progress

loader.py deliberately runs in one transaction: all-or-nothing is right for a fast load. Copying that shape here would be a plausible-looking mistake. Embedding is slow and can crash midway (that's the whole "fail loudly" design), and with one transaction a crash rolls back every embedding already computed — "a re-run resumes" would be false. So embed.py connects with autocommit=True and each Chunk's row is committed as it's produced. The test makes the second call raise, asserts the exception propagates, asserts the first Chunk's row survived, then re-runs and asserts only the missing Chunk is embedded.

4. Getting the migration into both databases

Files in init/ run in name order: 002 creates regdocs_test and copies 001's schema into it, so 003 runs after that copy and the test database wouldn't get the new table. 002's trick (\i the other file) can't be reused directly, because a file that \is itself recurses forever. The fix uses a psql variable as a flag: \if :{?applied_to_test} is false the first time, so it sets the flag, runs \c regdocs_test, and \is the same file; on that second pass the flag is defined and the block is skipped. The DDL is written once and runs twice. Verified from an empty volume in a scratch container, and again by applying it to the live one. Two gotchas along the way: Git Bash rewrites /docker-entrypoint-initdb.d/... into a Windows path (MSYS_NO_PATHCONV=1 stops it), and init scripts never re-run on an existing volume, so the README tells existing containers how to apply 003 by hand.

What /code-review caught

Review results

Spec axis: every acceptance criterion met; the four deviations above were each judged justified by the spec's own stated goals. Standards axis: no hard violations, but several stale comments, all fixed in a follow-up commit:

  • 001_schema.sql still said pgvector "isn't used by any column yet" — false the moment 003 landed.
  • upsert_immutable's docstring still said "whose id already exists" and listed only three tables, after I'd generalised it.
  • Two spots where Python behaviour (list(...) on the library's return value, str(float) round-tripping) deserved the line-by-line explanation this repo asks for.

The reviewers found no logic bug; the design corrections above were made while building. The lesson matches #19's: comments describing a shared helper rot silently when the helper changes.

Judgement calls left as they are

The separate chunk_id index is redundant with the primary key's leading column, but the ticket explicitly asks for it. The test module imports its fixtures from test_loader.py rather than a shared conftest.py — a reasonable cleanup, but out of this ticket's scope. EMBEDDING_DIMENSIONS (768) and the SQL's vector(768) must be kept in agreement by hand.

What's next

The shared spine is complete: documents, chunks, and their vectors all live in Postgres. Retrieval is next — embed the user's question with the "search_query: " prefix, ask pgvector for the nearest Chunk vectors, and add the similarity index once there's a real query to tune it against.
