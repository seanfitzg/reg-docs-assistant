Issue #43 — Finding personal data in a question, and keeping it out of storage

If someone types their email address or card number into the assistant, the system should still answer them, but it must not write that personal data into its permanent record. This issue makes the pipeline notice personal data, raise a warning flag, and store placeholders such as [REDACTED:EMAIL] instead. Follows issue #42's writeup.

Start here: what is this project?

RegDocs Assistant answers questions about Irish financial-regulation documents (the Central Bank's rules and consultation papers, for example). It uses a pattern called RAG (retrieval-augmented generation): when a question comes in, the system first retrieves the few passages of the documents most likely to contain the answer, then hands those passages and the question to a language model, which generates the written answer. The model is only allowed to rely on the passages it was given, and it cites them.

Because this is meant to resemble a system used in a regulated industry, every question and answer is saved as an Event: a permanent record that says what was asked, what was retrieved, which model answered, and what it said. Events are append-only. They are never edited or deleted, so there is always a trustworthy audit trail.

The pipeline that produces an Event has four fixed stages, called Steps:

classify → retrieve → draft → verify

This issue is about the first Step, classify. Its job is to look at the question before anything else happens and raise Flags: short markers on the Event, such as pii_detected, that say "someone should know about this".

Where things stood before this issue

Issues #40 to #42 built the retriever, the four-Step graph, and a real draft Step with citations. But classify was a placeholder: it did nothing, was recorded under the model name "stub", and every Event had an empty flags list. A question like "My email is jane@x.ie, how much notice must a firm give?" went straight through, and the Event saved to permanent storage contained the email address word for word.

The problem, and the core idea

That is a real problem. PII (personally identifiable information: email addresses, phone numbers, bank account numbers, national ID numbers, card numbers) should not sit in a permanent audit log unless there is a reason for it to. And because Events are append-only, it cannot be cleaned up afterwards. The only moment to remove it is before the Event is written.

The core idea of the fix has three parts:

  1. Detect once. classify scans the question with a set of rules and gets back a list of matches: what kind of PII, and exactly where in the text.
  2. Use that one list twice. Any match raises the pii_detected Flag, and the same matches drive the redaction. The Flag and the placeholders can never disagree, because they come from the same detections.
  3. Redact late. The pipeline carries on with the original text, so the answer is just as good. Only when the finished Event is assembled are the matches swapped for placeholders.

The concepts

Concept: a guardrail that annotates instead of blocks (ADR-0008)

A guardrail is a check that runs around an AI system to catch problems the model itself won't. Some guardrails stop the pipeline. The project does that for suspected prompt injection (someone trying to trick the model), because letting hostile text flow further into the model only gives it more chances to cause harm. PII is different. A person asking a legitimate question with their email in it is a storage problem, not a processing problem: answering them is fine, and only what ends up on disk needs care. So pii_detected deliberately does not halt anything. It raises a Flag and triggers Redaction, and that's all.

Concept: rules, not a model, for the first version

You could ask an AI model "does this text contain personal data?". For structured identifiers, plain rules are better: they are instant, free, run offline, give the same answer every time, and can be tested exactly. The rules here are regular expressions (patterns that describe the shape of a piece of text, like "letters, then @, then a domain") plus, for the riskier kinds, a checksum. The trade-off is that rules only find things with a recognisable shape. A person's name or home address typed into a sentence has no fixed shape, so rules cannot find it. That limit is documented, not hidden.

Concept: checksums cut false alarms

A 16-digit number is not necessarily a card number; it could be a reference or an order id. Real card numbers satisfy a built-in arithmetic test, the Luhn check: double every second digit from the right, add everything up, and the total must end in 0. IBANs carry a check too (a remainder of 1 when the rearranged number is divided by 97), and so do Irish PPSNs. The last letter of a PPSN is computed from the seven digits:

1234567T   digits weighted 8,7,6,5,4,3,2   →   1·8 + 2·7 + 3·6 + 4·5 + 5·4 + 6·3 + 7·2 = 112
           112 mod 23 = 20                  →   position 20 of "WABCDEFGHIJKLMNOPQRSTUV" (W is position 0) is T  ✓

So the rule only reports a PPSN, card or IBAN if the number passes its own check. 1234567A has the right shape but the wrong letter, so it is treated as an ordinary reference and left alone. If you have written input validators in .NET, this is the same idea as validating a check digit before accepting an ISBN.

Concept: why redact late, and why the pipeline still sees the original

If the question were redacted first, the later Steps would be working with [REDACTED:EMAIL] in place of the real text. For a question like "email me the answer at jane@x.ie" that could change what the model says. Redaction exists to protect storage, not to change how the question is processed, so the order is: run all four Steps on the original text, and only then build the Event with placeholders in it. If you think in event-sourcing terms, this is "scrub the data before you append the event", because once an event is appended it can never be changed.

Concept: why the answer is redacted by echo, not by scanning it (ADR-0034)

The question is scanned. The answer is not. Instead, wherever the answer repeats a value that was found in the question, that value is swapped for its placeholder. The reason is that answers legitimately quote the source documents, and a source document might contain a public contact email for the Central Bank. Scanning the answer would blank that out and make a correct answer worse, to protect nothing. The cost is that PII the model invents, or an echo it writes in a different format, is missed. That is also documented.

What the code does now

Detecting

The new file track-b/src/regdocs_track_b/pii.py has a function detect_pii(text). It returns one PiiMatch per hit, with the kind, the start and end position, and the matched text:

detect_pii("Email jane@x.ie or call 087 123 4567")

[PiiMatch(kind="EMAIL", start=6,  end=15, text="jane@x.ie"),
 PiiMatch(kind="PHONE", start=24, end=36, text="087 123 4567")]
KindWhat it matchesExtra check
IBANTwo letters, two digits, then groups of letters and digitsmod-97 checksum
CARD13 to 19 digits, spaces or hyphens allowed betweenLuhn checksum
PPSNSeven digits and one or two letterscheck-letter calculation
EMAILname, @, domainnone
PHONEIrish formats: +353…, 00353…, or a leading 0prefix can't start with 0

The rules run in the order shown. A stretch of text claimed by an earlier rule is skipped by later ones, so the digits inside an IBAN are never also reported as a phone number or a card.

Flagging

In graph.py, classify now calls detect_pii on the question. If there are any matches it adds "pii_detected" to the graph's flags. It also stores the matches in the graph's state, so later code can reuse them. The Step is recorded under the model name "rules" (no model is involved), where before it said "stub". Nothing else in the pipeline changes: retrieve, draft and verify run exactly as before, on the original text.

Redacting

When the graph finishes, answer_question assembles the Event. This is the one place that changes what is stored:

query:  redact_query(question, matches)        # replace each matched span, by position
answer: redact_answer(final_answer, matches)   # replace repeats of the same values
flags:  final["flags"]                         # ["pii_detected"] or []

A worked example, with a fake model that answers "We will reply to jane@x.ie within 30 days.":

Question asked   My email is jane@x.ie, how much notice must a firm give?
Saved query      My email is [REDACTED:EMAIL], how much notice must a firm give?

Model's answer   We will reply to jane@x.ie within 30 days.
Saved answer     We will reply to [REDACTED:EMAIL] within 30 days.

Saved flags      ["pii_detected"]
Retrieved Chunk  "Write to info@centralbank.ie for queries."   (stored untouched)

The retrieved Chunk text is left alone on purpose. It is public source text, not something the user typed. When the answer echoes a value, it is replaced only as a whole value, so jane@x.ieee is not cut into [REDACTED:EMAIL]ee.

What this does not catch

Limits, documented in the Track B README

Names and addresses. "John Murphy of 12 Main Street" passes through unchanged. Finding those needs a model that understands language (named-entity recognition), which is a separate piece of work. Foreign phone numbers and Irish freephone/premium numbers are missed. Reformatted echoes. If the question says 087 123 4567 and the model writes 0871234567, the answer is not redacted. PII the model makes up is never scanned for. Typos. A card or PPSN with a mistyped digit fails its checksum and is treated as ordinary text.

Try it yourself

One test shows the whole idea from question to stored Event:

uv run pytest track-b/tests/test_graph_pii.py::test_the_event_stores_typed_placeholders_instead_of_the_pii -v

It sends "My email is jane@x.ie, how much notice must a firm give?" through the real graph, with a fake model that answers "We will reply to jane@x.ie within 30 days.", and checks that the finished Event holds placeholders in both the query and the answer and still validates against the shared Event schema.

Ways to poke at it:

  • Right after event = _event(...) in that test, add print(event) and run with -s. You will see the whole Event, including the pii_detected flag and the four Steps.
  • Change the fake model's answer to "We will reply to jane@x.ieee" and watch the assertion fail. The expected text no longer matches, because the extra letters mean it was not an echo of the email, so it is left alone.
  • Change the email in the question to jane at x dot ie. The Flag disappears and the query is stored as typed, because nothing in that text has the shape of an email. That is the rule-based limit, seen directly.

Why this test and not the others: the detector tests in test_pii.py check each rule in isolation, which is useful but doesn't show how the pieces fit. This test is the only one that shows detection, the Flag, the late redaction of both fields, and schema validity in a single run, and it needs nothing running except Python.

Summary

Before this issue, the first pipeline Step did nothing and any personal data typed into a question was saved permanently in the audit record. Now classify scans the question with deterministic rules (email, Irish phone, IBAN, PPSN and card number, the last three checked with their own checksums), raises a pii_detected Flag that does not stop the pipeline, and hands the matches forward. The model still answers using the original text, and only when the Event is assembled are the matches replaced with typed placeholders in the stored query and answer, using the same detections that raised the Flag. Retrieved source text is never redacted. The approach finds structured identifiers but not names or addresses in ordinary sentences, and that limit is written down in the README.
