Issue #18 — /store's Postgres+pgvector schema

What got built, and the Docker/Postgres concepts behind it. Written for "some Docker experience, not a huge amount."

Where this fits

Ingestion (already built, in /ingestion) turns corpus PDFs into Document and Chunk JSON files, but that output only ever lives on disk — regenerable from the PDFs at any time, never treated as real storage. Issue #18 is about giving those records somewhere durable and queryable to actually live: a Postgres database, defined in a new /store folder.

This ticket is schema only — bring up the database, create the tables, nothing writes real data into it yet. A separate ticket (#19, blocked by this one) builds the Python loader that actually populates it from ingestion/output.

docker-compose.yml, briefly

You've used Docker before, so the container concept isn't new — this is about what docker-compose.yml specifically declares, and why it's the right tool here instead of a bare docker run.

Concept

docker-compose.yml is a declarative description of one or more services and how they're configured — image, environment variables, ports, volumes, health checks — checked into the repo so docker compose up reproduces the exact same setup on any machine. Think of it as the Docker equivalent of a .csproj's package references plus a launch profile: instead of everyone remembering (or mistyping) a long docker run command with a dozen flags, the flags live in a file, in version control, next to the code that needs them.

services:
  postgres:
    image: pgvector/pgvector:pg16
    environment:
      POSTGRES_USER: regdocs
      POSTGRES_PASSWORD: regdocs_dev_only
      POSTGRES_DB: regdocs
    ports:
      - "5432:5432"
    volumes:
      - ./init:/docker-entrypoint-initdb.d
      - regdocs_data:/var/lib/postgresql/data

The image: pgvector/pgvector

pgvector is a Postgres extension — an add-on that gives Postgres a new column type (vector) and new index types for fast similarity search over those vectors. That's the mechanism behind semantic search / RAG retrieval: an embedding model turns a chunk of text into a vector, and pgvector lets you ask "which stored vectors are closest to this query vector?" efficiently.

This ticket doesn't use any of that yet — no vector column exists in the schema, and no embedding model has been chosen. But swapping the underlying Docker image later (from plain postgres to pgvector/pgvector) would be more disruptive than just having it available from day one, so the image is pgvector-enabled now, unused, ready for the follow-up embeddings ticket to add a column and start using it.

Init scripts: how the schema gets created automatically

Concept

The official Postgres Docker image (and pgvector's, which is built on top of it) has a built-in convention: on its very first startup — meaning the data directory is empty — it runs every .sh and .sql file it finds inside /docker-entrypoint-initdb.d, in filename order. Mounting a local folder to that path is how a container "seeds itself" with no manual step. It's the closest Docker analogue to an EF Core seed migration that runs automatically on first launch — except it's just raw SQL, no ORM or migration-history table involved.

docker-compose.yml mounts ./init to that path, and init/001_schema.sql is the one file in there. It runs automatically the first time docker compose up starts the container against a fresh volume.

The gotcha

"First startup" is defined by the data volume being empty, not by the SQL file being new. If you edit 001_schema.sql after the container has already initialized once, docker compose up will not re-run it — Postgres has no idea the file changed, it just sees an already-initialized data directory and starts normally. I hit exactly this while fixing the bugs below: I had to run docker compose down -v (the -v drops the volume too, not just the container) before docker compose up -d would pick up the corrected SQL.

The schema itself

Three tables, one per domain concept this project's glossary (CONTEXT.md) already defines: Document (one regulatory PDF), Chunk (one retrievable/citable passage from a Document), and Chunking Generation (one run of a chunking strategy over a Document — Documents can be re-chunked, and old Generations stick around rather than being overwritten, so past answers can still be replayed against the exact context that produced them).

TableKey columnsNotes
documentsid, title, active_chunking_generation_id, supersedesactive_chunking_generation_id says which Generation retrieval currently searches
chunking_generationsid, document_id, chunking_strategynew to this ticket — earlier design docs never gave this its own table
chunksid, document_id, chunking_generation_id, locator, textno embedding column yet

One deliberate choice worth calling out: these are ordinary typed columns (TEXT, DATE, …), not a JSONB blob per row. Elsewhere in this project's plan, a separate "audit event" store does use JSONB, because an event's shape genuinely varies by event type. Documents and Chunks don't have that problem — each has exactly one fixed shape — so typed columns let Postgres itself enforce "this field is required" and "this must point at a real row" instead of pushing that checking into application code.

The tricky part: a circular foreign key

A foreign key is a constraint that says "this column's value must exist as a primary key in that other table" — Postgres checks it on every insert/update and rejects anything that would leave it pointing at nothing. Straightforward, usually.

Here, though, documents.active_chunking_generation_id needs to point at a row in chunking_generations — but every row in chunking_generations also has a document_id pointing back at documents. Each table needs the other to exist first, which is impossible if you try to declare both foreign keys inline in their respective CREATE TABLE statements — whichever table you create second can reference the first, but not the other way around.

What we did

Create documents first, with active_chunking_generation_id as a plain column and no foreign key yet. Then create chunking_generations, which can reference documents inline since it already exists. Then, as a separate statement, ALTER TABLE documents ADD CONSTRAINT ... FOREIGN KEY (active_chunking_generation_id) REFERENCES chunking_generations (id) — bolting the second half of the relationship on once both tables exist.

CREATE TABLE documents (
    id TEXT PRIMARY KEY,
    ...
    active_chunking_generation_id TEXT   -- no FK yet
);

CREATE TABLE chunking_generations (
    id TEXT PRIMARY KEY,
    document_id TEXT NOT NULL REFERENCES documents (id),  -- fine, documents exists
    ...
);

ALTER TABLE documents
    ADD CONSTRAINT fk_documents_active_chunking_generation
    FOREIGN KEY (active_chunking_generation_id)
    REFERENCES chunking_generations (id);   -- now this exists too

What /code-review caught

After the schema was up and manually verified, I ran this project's /code-review step (part of the standard implementation workflow here) before committing. It found two real integrity gaps in the foreign-key design above — worth walking through since the bug is genuinely non-obvious.

The bug

A single-column foreign key on chunking_generation_id only proves the referenced Generation exists somewhere — not that it belongs to the same Document the Chunk itself claims. Nothing stopped a row like: 

-- doc-A's chunk, pointing at doc-B's generation. Both plain FKs pass individually.
INSERT INTO chunks (id, document_id, chunking_generation_id, ...)
VALUES ('c1', 'doc-A', 'gen-belonging-to-doc-B', ...);

Same problem on documents.active_chunking_generation_id: it could legally point at a Generation belonging to a completely different Document, which would mean retrieval serves one Document's chunks under another Document's identity.

The fix: composite foreign keys

A foreign key can cover more than one column at once, checked as a pair. First, chunking_generations gets a UNIQUE constraint on (document_id, id) together — giving that pairing something to be referenced against, not just id alone. Then both the risky relationships get upgraded to composite foreign keys against that pair: 

ALTER TABLE chunking_generations
    ADD CONSTRAINT uq_chunking_generations_document_id_id
    UNIQUE (document_id, id);

-- chunks: document_id and chunking_generation_id must belong together
ALTER TABLE chunks ADD CONSTRAINT fk_chunks_document_chunking_generation
    FOREIGN KEY (document_id, chunking_generation_id)
    REFERENCES chunking_generations (document_id, id);

-- documents: the active pointer must belong to *this* document
ALTER TABLE documents ADD CONSTRAINT fk_documents_active_chunking_generation
    FOREIGN KEY (id, active_chunking_generation_id)
    REFERENCES chunking_generations (document_id, id);

After this, the bad insert above is rejected by Postgres itself — no application code has to know to check it.

The other bug: an unconstrained "closed set"

chunking_strategy is one of exactly three known values (clause_numbered, heading_sections, academic_sections — an existing design decision, ADR-0014). The column was plain TEXT with nothing stopping an arbitrary string from being stored. Fixed with a CHECK constraint, the same "let the database enforce it" philosophy as the foreign keys above: 

chunking_strategy TEXT NOT NULL CHECK (
    chunking_strategy IN ('clause_numbered', 'heading_sections', 'academic_sections')
)

How it was verified

This ticket has no automated tests (that arrives with #19's loader, tested against a real container). Instead, verification was a manual session against the running container — the kind of thing you'd normally do once in psql and then throw away, recorded here because it's the actual proof the schema works:

Verified
  • \dx — the vector extension is installed
  • \d on each table — columns, types, nullability, and every foreign key/check constraint match the design
  • A same-document insert (Document → its own Generation → a Chunk of that Generation) succeeds
  • A cross-document chunk insert is rejected by fk_chunks_document_chunking_generation
  • Pointing a Document's active_chunking_generation_id at another Document's Generation is rejected
  • An invalid chunking_strategy value is rejected by the CHECK constraint
