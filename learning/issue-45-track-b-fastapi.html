Issue #45 — Putting the pipeline behind a web address

Until now the assistant could only be driven from Python code and tests. This issue wraps it in a small web service: send it a question over HTTP and get back an answer, its citations and any warning flags; look up the stored record of any past answer by id. Follows issue #44's writeup.

What the project is, and where we were

RegDocs Assistant answers questions about regulatory documents. Behind the scenes a four-step pipeline (classify, retrieve, draft, verify) finds relevant passages ("Chunks"), has a language model write an answer that cites them, and builds an Event: the permanent record of the question, answer and what happened along the way. Issue #43 made that record redact personal data; issue #44 gave Events a permanent, edit-proof database table and a writer. But there was still no way for anyone to use the thing except by writing Python.

The problem, and the core idea

A demo needs an address you can send a question to. The core idea is two endpoints and almost no logic of their own:

POST /query→run the graph→write the Event→return id, answer, citations, flags
GET /events/{id}→read the row→return it, or 404

All the interesting work already existed. The API is a thin layer that connects HTTP to it.

Concept: FastAPI (the ASP.NET Core of Python)

FastAPI is a Python web framework. If you know ASP.NET Core minimal APIs, it is very close: you write a function, decorate it with the route (@app.post("/query")), and the framework handles routing and JSON. The request body is described by a pydantic class (QueryRequest), which plays the role of a DTO with validation attributes: an empty question is rejected with a 422 before your code runs. The return type (QueryResponse) describes the response and also drives the auto-generated docs page at /docs, the same job Swagger does in .NET.

One detail worth knowing: the handlers are plain def, not async def. The graph does blocking work (database calls, a model call). FastAPI runs plain-def handlers on a pool of worker threads, so a slow question doesn't freeze other requests. An async def handler that blocked would stall the whole server.

Concept: a seam you can inject fakes into

The app is built by create_app(graph, db_url), which takes the already-built graph and database URL as arguments. This is constructor injection, the way you would register services in a .NET WebApplicationFactory test. Tests pass a graph built from a fake retriever and a scripted fake chat model, so they run offline and deterministically. Production uses create_default_app(), which builds the real local models (Ollama's qwen2.5:7b-instruct for drafting, nomic-embed-text for retrieval). Language models are non-deterministic, so putting the model behind an injectable seam is what makes the API testable at all.

What the code now does

POST /query

request:   {"question": "How much notice must a firm give?"}
response:  {"event_id": "3f1c...",
            "answer": "Thirty days' notice. [1]",
            "citations": [{"marker": 1, "chunk_id": "c-1",
                           "document_id": "doc-a", "locator": "3.1"}],
            "flags": []}

Citations are resolved by code, never written by the model (ADR-0010). They are not part of the stored Event, because the shared Event schema has no field for them. So the pipeline's run_question now returns the Event and its citations side by side. The older answer_question still exists and returns only the Event.

The answer in the response is the stored answer, so if the model echoed back an email address the user typed, it appears as [REDACTED:EMAIL] in the response too. That keeps the response from containing anything the permanent record doesn't.

GET /events/{id}

Reads the row from the events table (read_event) and returns the stored Event, or HTTP 404 if the id is unknown. Because citations aren't stored, only the POST response carries them.

Try it yourself

Needs the Postgres container running. No Ollama needed for the test.

The one test that teaches the whole flow: test_the_event_a_query_names_is_stored_and_retrievable in track-b/tests/test_api.py.

python -m pytest track-b/tests/test_api.py::test_the_event_a_query_names_is_stored_and_retrievable

It POSTs a question through FastAPI's in-process TestClient (no real server, no network), takes the event_id from the response, GETs that id back, and checks the stored Event matches the schema. To poke at it: add print(posted) and print(event) and run with -s to see exactly what the API returns versus what is stored (notice the stored Event has no citations). Change the scripted answer in _client() to "Thirty days. [9]" and watch the unresolvable marker be stripped and the citations list come back empty.

It was chosen over the others because it exercises both endpoints and the database in one go; the remaining tests (404, PII redaction, empty question) are variations on it.

To run it for real, follow "Running the API" in track-b/README.md and open http://127.0.0.1:8000/docs.

Summary. The pipeline now has a front door: POST /query runs a question through the graph, stores the resulting Event with the issue-44 writer, and returns its id, answer, citations and flags; GET /events/{id} reads a stored Event back or returns 404. The app is built from an injected graph, so tests drive it in-process with fakes against the test database, while create_default_app wires the real local models for running it locally.
