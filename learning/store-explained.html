1. What the store is

The store is a Postgres database running in Docker, with the pgvector extension added so Postgres can hold and search embedding vectors. It's where everything the app knows ends up living:

  • the regulatory Documents (about 20 of them),
  • the Chunks those Documents were cut into (roughly 2,000),
  • an embedding for every searchable Chunk,
  • and an append-only log of Events recording every question the app answered.

Before the store existed, ingestion wrote JSON files to ingestion/output/. Those files are still produced, but they're treated as a regenerable by-product, not the real storage (ADR-0012). The store is the source of truth that retrieval, the eval harness and Track B all query.

.NET analogy

Think of /store as the database project in a .NET solution: a set of numbered SQL scripts that build the schema, plus two small console apps (loader.py, embed.py) that populate it. There's no ORM and no migration framework like EF Migrations. It's plain SQL files, run in filename order (ADR-0020/0021/0022).

2. Where it sits in the pipeline

Ingestion reads the PDFs and writes Document and Chunk JSON to ingestion/output/.
▼
loader.py reads that JSON (plus manifest.json) and inserts documents, chunking_generations and chunks rows.
▼
embed.py sends each active Chunk's text to the local Ollama model and stores the 768-number vector in chunk_embeddings.
▼
Retrieval (the eval harness, Track B's retriever) embeds a question and asks Postgres for the nearest Chunk vectors.
▼
Track B writes one row to events for every question it answers.

The loader is deliberately a separate script, not a step inside ingestion (ADR-0020). Ingestion stays a pure "PDFs in, JSON out" transformation that runs and tests without a database, and the loader can be re-run on its own after a schema change without re-parsing every PDF.

3. The tables at a glance

Read top to bottom, the diagram says: a Document has one or more Chunking Generations and points at one of them as active. Each Generation has many Chunks. Each Chunk can have one embedding per model. Events sit on their own.

4. Each table in plain words

TableOne row is…ExampleDefined in
documentsOne regulatory publication at a point in time.doc-04-cp54-second-consultation-consumer-protection-codeinit/001_schema.sql
chunking_generationsOne run of a chunking strategy over one Document: "this Document, cut this way".doc-04-…-gen-1, strategy clause_numberedinit/001_schema.sql
chunksOne searchable, citable passage, with its locator (where it is in the Document) and its text.locator 3.12 or Mortgage Incentives (p. 44)init/001_schema.sql
chunk_embeddingsOne Chunk's vector, produced by one named embedding model.(…-chunk-007, nomic-embed-text, [0.013, -0.041, … 768 numbers])init/003_chunk_embeddings.sql
eventsOne thing that happened: a question answered, an answer flagged or overridden.event_type = 'QueryAnswered', full detail in payloadinit/004_events.sql

Why typed columns for most tables, but JSONB for events?

Documents and Chunks have exactly one fixed shape, defined once in /schema. Typed columns let Postgres enforce NOT NULL and foreign keys, and let queries join on document_id directly (ADR-0022).

Events differ: a QueryAnswered has different fields from an AnswerOverridden, so no fixed column set fits all of them. That's the one place a JSONB blob is right. Two fields audit queries filter on first, event_type and recorded_at, are pulled out into real columns (ADR-0031).

5. Big idea 1: nothing is ever edited

Every row in the store is immutable once written. The loader never updates, deletes or truncates. Every insert goes through one helper in db.py:

INSERT INTO chunks (id, document_id, ...) VALUES (...)
ON CONFLICT (id) DO NOTHING

If a row with that id already exists, it's silently skipped, not overwritten. So running the loader twice is a safe no-op, and running it after adding a new Document only adds the new rows.

That works because every id is deterministic: derived from stable inputs such as the PDF filename (doc-04-…, doc-04-…-gen-1, doc-04-…-gen-1-chunk-007), never random. The same input always produces the same id.

Event sourcing analogy

This is your event store's "append, never rewrite" rule applied to reference data. A correction to a Document isn't an edit. It's a new Document with supersedes pointing at the old one, the way a compensating event is appended rather than history rewritten. A side effect worth knowing: if you fix a typo in ingested JSON without changing the id, the loader ignores the fix. The original row wins, on purpose.

The one deliberate exception is documents.active_chunking_generation_id. It's a pointer that is meant to move, so the loader re-applies it on every run (ADR-0004). supersedes is set only the first time a Document is loaded.

6. Big idea 2: Chunking Generations and the active pointer

"Chunking" means cutting a long PDF into passages small enough to search and hand to an LLM. There's more than one way to do it: by numbered clause, by heading, by academic section. You'll want to try better chunkers over time.

The naive approach would be to delete a Document's old Chunks and insert new ones. That breaks two things:

  • Replay. An old Event cites specific Chunks. If they're deleted, you can't reconstruct what the app saw when it answered.
  • Comparison. You can't run the eval against the old chunking and the new one side by side.

So instead, each re-chunking produces a new Chunking Generation: a fresh, complete set of Chunks with new ids. Old generations stay in the table. The Document carries one pointer, active_chunking_generation_id, saying which generation retrieval should search.

documents
  doc-04   active_chunking_generation_id = doc-04-gen-2   ← retrieval searches this one

chunking_generations
  doc-04-gen-1   clause_numbered    (kept, never searched)
  doc-04-gen-2   heading_sections   (active)
Not built yet

The store is ready for multiple generations, but ingestion doesn't produce them yet. pipeline.py hardcodes generation_number = 1, so every run writes the same …-gen-1 ids. Rerunning ingestion after changing a Document's chunking does not create gen-2. Instead, the loader keeps the existing gen-1 rows, adds any extra new Chunk ids into gen-1, and leaves the old strategy in place. To truly re-chunk today, reset the database (docker compose down -v, which also wipes events) and reload.

Why a single pointer on the Document, rather than an is_active flag on each generation? A flag could, through one bug, end up true on two generations or false on all of them. One pointer can only ever name one (ADR-0004).

7. Big idea 3: the composite foreign keys

This is the subtlest part of 001_schema.sql. A plain foreign key proves a referenced row exists, but not that it belongs to the right parent.

Consider this bad row:

documents:  id = doc-04,  active_chunking_generation_id = doc-09-gen-1

A plain FK on active_chunking_generation_id would accept it, because doc-09-gen-1 does exist. But it's doc-09's generation, so retrieval for doc-04 would silently search another Document's Chunks.

The fix is to make the foreign key cover two columns:

-- give (document_id, id) its own identity to point at
ALTER TABLE chunking_generations ADD CONSTRAINT ... UNIQUE (document_id, id);

-- "my id AND my active generation" must match "a generation's document_id AND its id"
ALTER TABLE documents ADD CONSTRAINT fk_documents_active_chunking_generation
    FOREIGN KEY (id, active_chunking_generation_id)
    REFERENCES chunking_generations (document_id, id);
documents rowPlain FKComposite FK
doc-04 → doc-04-gen-2acceptedaccepted
doc-04 → doc-09-gen-1accepted (bug!)rejected
doc-04 → NULL (not chunked yet)acceptedaccepted (a NULL skips the check)

chunks uses the same trick, with (document_id, chunking_generation_id), so a Chunk can't claim a generation that belongs to a different Document from the one it claims.

DDD analogy

It's an aggregate invariant ("a Document's active generation is one of its own generations") pushed down into the database, so no code path, test fixture or hand-typed SQL can break it. The project's rule throughout is constraints, not prose: if the domain says it, the schema enforces it. The CHECK on chunking_strategy is the same idea.

One consequence: documents and chunking_generations reference each other, a circular dependency. You can't create both foreign keys in one CREATE TABLE, which is why 001_schema.sql adds the active-pointer FK afterwards with ALTER TABLE. The loader faces the same chicken-and-egg problem (section 10).

8. Big idea 4: embeddings and pgvector

Concept: embeddings

An embedding is a list of numbers (here 768 of them) that a neural network produces from a piece of text. The model is trained so that texts with similar meaning produce vectors pointing in similar directions. "Banks must hold minimum capital" and "Credit institutions are required to maintain minimum own funds" share few words but end up close together. A recipe for bread ends up far away.

Search then becomes geometry: embed the question, find the stored vectors pointing most nearly the same way. That's the "retrieval" in RAG.

embed.py uses nomic-embed-text, a small model run locally by Ollama, so no data leaves the machine and no API costs are incurred. pgvector adds a vector(768) column type and distance operators such as <=> (cosine distance) to Postgres. Postgres rejects a vector of any other length at insert time, so a wrong-sized model can't slip in unnoticed.

Three design decisions

  1. A separate table keyed by (chunk_id, embedding_model), not an embedding column on chunks (ADR-0024). A column would be overwritten the first time you tried a second model, and the eval could no longer compare the two. As a separate table, a second model just adds rows beside the first. It's the same "old stays, new is additive" pattern as Chunking Generations.
  2. Only the active generation is embedded (ADR-0025). Embedding is the one expensive step: a model call per Chunk. Inactive generations are never searched, so embedding them would be wasted work.
  3. Chunk text is prefixed with "search_document: " before embedding (ADR-0026), and questions later with "search_query: ". nomic-embed-text was trained this way: it places stored passages and search questions in vector space differently. Leave the prefix off and search still works, just measurably worse. The prefix is only sent to the model. chunks.text is stored exactly as ingested.

Built to resume after a crash

The loader runs in one big transaction: all or nothing. embed.py deliberately doesn't. It uses autocommit, saving each embedding the moment it's computed, and its query only selects Chunks that don't yet have an embedding for this model:

SELECT chunks.id, chunks.text
FROM chunks
JOIN documents                              -- only the active generation
  ON chunks.document_id = documents.id
 AND chunks.chunking_generation_id = documents.active_chunking_generation_id
LEFT JOIN chunk_embeddings                  -- ...that isn't embedded yet
  ON chunk_embeddings.chunk_id = chunks.id
 AND chunk_embeddings.embedding_model = 'nomic-embed-text'
WHERE chunk_embeddings.chunk_id IS NULL

So if Ollama dies at Chunk 1,400, re-running picks up at 1,401. And it fails loudly on the first error, so a systemic problem (Ollama not running, model not pulled) shows up on Chunk 1, not after an hour.

9. Big idea 5: the append-only events table

Every question Track B answers becomes an Event row: what was asked (with personal data already redacted), which Chunks were cited, any flags raised. This is the audit trail, and it must never change after being written.

Instead of trusting every caller to behave, 004_events.sql installs a trigger that fires before any UPDATE or DELETE and raises an error:

CREATE TRIGGER events_are_immutable
    BEFORE UPDATE OR DELETE ON events
    FOR EACH ROW EXECUTE FUNCTION reject_event_change();
-- → ERROR: events is append-only: UPDATE is not allowed

A correction is always a new Event. recorded_at is stamped by the database's clock (DEFAULT now()), not passed in by the app, so it can't be forged or skewed. The app validates each Event against its JSON Schema before inserting. The database stores the payload without re-checking its shape.

One deliberate gap: row triggers don't fire on TRUNCATE. That stays a privileged, deliberate act, and it's how the test helpers clear the test database between tests.

10. How the loader fills the tables

loader.py first validates the JSON in memory: every Chunk's Document exists, every strategy is valid, every active pointer names a real generation. Errors come out as clear messages, not raw foreign-key violations. Then, in one transaction, it writes in four phases. The order is forced by the circular references:

PhaseWritesWhy in this order
1documents, without supersedes or the active pointerThose two fields can point at rows that don't exist yet.
2chunking_generationsNeeds its Document, which now exists.
3UPDATE documents: set supersedes (new Documents only) and the active pointer (always)The rows both fields point at now exist.
4chunksNeeds both its Document and its Generation.

If anything fails, the whole load rolls back. Unlike ingestion, where one corrupt PDF shouldn't stop the others, a failure here means validated JSON doesn't fit the schema. That's a bug worth stopping for.

Chunking Generations aren't their own JSON files: they only appear as ids on Chunks. The loader derives them from the Chunks and reads each one's chunking_strategy from ingestion/manifest.json.

11. How retrieval reads it

This is (simplified) the entire retriever used by the eval harness and Track B. It's one SQL statement:

SELECT chunks.document_id, chunks.locator,
       1 - (chunk_embeddings.embedding <=> :question_vector) AS similarity
FROM chunk_embeddings
JOIN chunks      ON chunks.id = chunk_embeddings.chunk_id
JOIN documents   ON documents.id = chunks.document_id
               AND documents.active_chunking_generation_id = chunks.chunking_generation_id
WHERE chunk_embeddings.embedding_model = 'nomic-embed-text'
ORDER BY chunk_embeddings.embedding <=> :question_vector
LIMIT 10
  • <=> is pgvector's cosine distance: 0 = same direction, 1 = unrelated. 1 - distance turns it into a similarity score.
  • ORDER BY distance LIMIT 10 is "give me the 10 nearest neighbours".
  • The join on active_chunking_generation_id is where the active pointer earns its keep: old generations never come back.
  • Filtering on embedding_model is where the (chunk_id, embedding_model) key earns its keep: a second model's vectors could sit in the same table without interfering.

12. Two databases and the init scripts

docker compose up -d in store/ starts pgvector/pgvector:pg16. On the first start with an empty volume, Postgres runs every file in init/ in filename order:

FileDoes
001_schema.sqlEnables pgvector; creates documents, chunking_generations, chunks, their keys and indexes.
002_test_database.sqlCreates a second database, regdocs_test, and re-runs 001 inside it.
003_chunk_embeddings.sqlAdds chunk_embeddings to both databases.
004_events.sqlAdds events and its trigger to both databases.

Why two databases? Tests wipe tables between runs. Pointing them at regdocs_test means running the test suite can never destroy the real data you loaded into regdocs. Tests that need Postgres skip themselves (rather than fail) if the container isn't up.

How 003 and 004 reach both databases without a duplicate copy of the SQL: each file sets a psql variable as a "done" flag, reconnects to regdocs_test and re-includes itself. On the second pass the flag is set, so it doesn't loop forever.

Gotcha

Init scripts only run against an empty volume. If you change a schema file later, docker compose up won't re-apply it. Either reset (docker compose down -v, then up -d, then re-run the loader and embedder) or apply the single file by hand with psql -f, as store/README.md shows.

13. What isn't built yet

  • No vector index (hnsw / ivfflat). Every search compares the question against all ~2,000 vectors. At this size that's instant, and it's exact. Approximate indexes can miss true neighbours, which would muddy the eval's measurements. An index needs tuning against real query patterns, so it's deferred until it's needed.
  • No GIN index on events.payload. Deferred until a JSONB query is actually slow.
  • Inactive generations have no embeddings. If a Replay ever needs period-accurate vectors (not just period-accurate text), they won't exist. That's a known, accepted gap (ADR-0025).

14. Try it yourself

All of these need the container running (docker compose up -d in store/). None need Ollama: the tests inject a fake embedding client.

Test 1: only the active generation gets embedded

store/tests/test_embed.py::test_embeds_only_chunks_of_the_active_generation

python -m pytest store/tests/test_embed.py::test_embeds_only_chunks_of_the_active_generation -v

Shows: the loader and embedder working together. The fixture corpus has one Document with two generations: gen-1 (inactive, one Chunk) and gen-2 (active, two Chunks). After embed_chunks, only the two gen-2 Chunks have embeddings, and the fake client was called exactly twice.
Poke at it: in embed.py, delete the line AND chunks.chunking_generation_id = documents.active_chunking_generation_id and rerun. The inactive Chunk gets embedded too and the test fails. That one join line is the whole of ADR-0025.
Why this one: in one test it exercises the loader, Chunking Generations, the active pointer and the embeddings table, which is most of this page.

Test 2: the events table refuses edits

store/tests/test_events_table.py::test_delete_on_events_is_rejected

python -m pytest store/tests/test_events_table.py::test_delete_on_events_is_rejected -v

Shows: a DELETE FROM events raises the trigger's "append-only" error, and the row is still there afterwards. The guarantee lives in the database, not in Python.
Why this one: it's short and pure SQL, so the database-enforced rule is easy to see.

Poke the real data directly

cd store
docker compose exec postgres psql -U regdocs -d regdocs
-- how many Chunks per Document, active generation only
SELECT d.id, count(*) FROM documents d
JOIN chunks c ON c.chunking_generation_id = d.active_chunking_generation_id
GROUP BY d.id ORDER BY d.id;

-- try to break the composite FK (this should fail)
UPDATE documents SET active_chunking_generation_id = 'doc-09-cp158-consumer-protection-code-gen-1'
WHERE id LIKE 'doc-04%';

-- see the first 5 of a Chunk's 768 numbers
SELECT chunk_id, (embedding::real[])[1:5] FROM chunk_embeddings LIMIT 3;

For a feel of what similarity scores look like, run python -m regdocs_store.explore_embeddings (needs Ollama). It's a throwaway learning script that compares a handful of sentences and prints their similarity matrix, with and without the prefixes.

Summary

The store is a Postgres + pgvector database with five tables. documents, chunking_generations and chunks hold the corpus in typed columns. They're filled by a loader that only ever inserts, and protected by composite foreign keys so a Document's active pointer, and every Chunk, can only refer to a generation of the right Document. Re-chunking adds a new generation instead of replacing the old one, and the active pointer decides which one retrieval searches. chunk_embeddings holds one 768-number vector per Chunk per model, computed locally by Ollama for active Chunks only, with an asymmetric prefix the model relies on. Retrieval is one SQL query ordering by cosine distance. events is an append-only JSONB audit log whose immutability is enforced by a trigger. Throughout, the rule is the event-sourcing one: old data stays, new data is added beside it, and the schema enforces the domain's rules rather than leaving them to convention.
