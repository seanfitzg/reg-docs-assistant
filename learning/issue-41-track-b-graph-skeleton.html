Issue #41 — A four-node LangGraph that assembles a valid Event

Track B's first orchestration code. A LangGraph state graph runs classify → retrieve → draft → verify, times each node, and assembles an Event that validates against the shared event.schema.json. Two nodes are honest stubs, the retriever is the real one from #40 (ADR-0032), and the tests run offline against a scripted fake chat model.

Where this fits

#40 retriever → #41 graph skeleton → real classify / draft / verify → write Events to the store

The point of building the whole shape first, with fake insides, is that every later change plugs into a pipeline that already produces a schema-valid Event. Replacing the verify stub with a real groundedness score changes one function and one number, and the Event stays valid throughout.

The concepts

Concept: a LangGraph state graph is a typed state machine

You define a state (here a TypedDict holding the question, the retrieved Chunks, the answer and the list of Steps), a set of nodes (plain functions that take the state and return a partial update), and edges saying which node runs after which. graph.compile() turns that into something you can invoke. If you've hand-rolled state machines, this is the same idea: what a node returns is a patch merged into the state, and the edges are the transition table. Here the transitions are a straight line, which is what makes it a good skeleton. Later, a conditional edge can route straight to the end when no_chunks_retrieved halts the pipeline (ADR-0009).

Concept: reducers decide how a node's update merges

By default a node's returned key overwrites that key in the state. That would be wrong for steps: each node would erase the previous node's Step. Annotating the field as Annotated[list[dict], operator.add] tells LangGraph to combine old and new with +, so each node returns {"steps": [its_own_step]} and the list grows in run order. It's the same shape as event sourcing: nodes append facts, nothing edits an earlier one, and the final Event is a fold over what was appended.

Concept: why stubs say "stub", and why verify's confidence is 0.0

An audit trail that records a placeholder as if it were a real judgment is worse than a gap. So classify and verify are recorded under the model name "stub", and verify reports confidence: 0.0. Nothing downstream can mistake that for a real groundedness score (CONTEXT.md: Confidence is verify's score, never a model's self-report). Stub Steps are the honest version of "not built yet".

Concept: a scripted fake chat model

LLM output is non-deterministic, so a test can't assert on what a real model says. LangChain ships FakeListChatModel: you give it the responses it will return, in order, and it returns them. The draft node is then exercised through the real invoke call with a known answer, offline. The graph is built exactly as in production, with the real model swapped for the scripted one at the boundary.

Concept: monotonic clocks

Latency is measured with time.perf_counter, a monotonic clock: it only moves forward and ignores wall-clock changes. datetime.now() can jump (NTP sync, daylight saving) and give a negative or wildly wrong duration. It's the same reason .NET has Stopwatch next to DateTime.UtcNow. The clock is injectable, so the test passes a fake that advances 0.25 s per reading and asserts each Step took exactly 250 ms.

What was built

What I did

track-b/graph.py: build_graph(retriever, chat_model, draft_model_name, clock) returns the compiled graph, and answer_question(graph, question) runs it and assembles the Event (fresh UUID id, event_type: "QueryAnswered", empty flags, the Steps in order). Each node reads the clock before and after its work, and every Step costs 0 because everything runs locally. The retrieve node pins each Chunk's id, document id, text and score into its Step, so Replay can re-run against exactly what was retrieved (ADR-0005). Draft builds a plain "answer using only this context" prompt from the retrieved text. The test seam, agreed up front, is answer_question only.

Built test-first

The first test asserted only that the Event validates against the schema. A deliberately crude first cut passed it, with hard-coded zero latencies and an empty retrieved_chunks. The next three tests (order, cost and latency; "stub" models; pinned chunks) then failed for the right reasons, and the real implementation made them pass.

What code review caught

Bug: a blank answer silently produced an invalid Event

My first draft node returned response.content unchecked. The schema requires answer to be a non-empty string, so a model that returned "" (or, for some chat models, a list of content blocks rather than a string) would yield an Event that fails validation later, far from the cause. The fix: draft raises a ValueError naming the bad value, and a test pins it. Failing at the node that produced the problem is the same fail-loudly stance as ADR-0019.

Also: a comment that taught instead of explaining why

Review flagged a comment describing how the operator.add reducer works. The repo's rule is that comments carry the non-obvious why and library mechanics are explained in conversation, so it moved into the concept box above. The monotonic-clock note moved to the clock parameter it actually justifies.

Known gap, deliberately left

If retrieval returns nothing, the graph still runs draft and verify and raises no no_chunks_retrieved Flag. The Event is schema-valid, but it contradicts the domain rule that this Flag halts the pipeline at retrieve (ADR-0009). Halting is later work, and the header comment in graph.py says so, so it isn't a silent omission.
