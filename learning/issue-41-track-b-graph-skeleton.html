Issue #41, explained from the start

Building the empty "shape" of the question-answering pipeline before filling in the clever parts. No prior AI knowledge needed.

1. What is this project?

RegDocs Assistant answers questions about Irish financial-regulation documents, and keeps a permanent, auditable record of every answer. You ask a question, it finds relevant passages in the real documents, has an AI model write an answer from them, and stores a record of exactly what happened.

Concept: RAG (Retrieval-Augmented Generation)

An AI language model (an "LLM") doesn't know your documents, and when it doesn't know something it tends to make up a plausible answer. RAG fixes this in two moves:

  1. Retrieve: search your documents for the few passages most relevant to the question.
  2. Generate: put those passages in the prompt and tell the model "answer using only these."

It's an open-book exam: the model gets the relevant pages instead of answering from memory.

Vocabulary used in this project (from CONTEXT.md): a Chunk is one passage cut from a regulatory Document; a Step is one stage of the pipeline; an Event is the permanent record of one question and its whole answer, including all its Steps.

2. Where we were before this issue

Issue #40 built the retriever: give it a question, it searches the database and returns the best-matching Chunks. That is the "retrieve" half of RAG, on its own. Nothing yet connected it to a model, and nothing produced an Event.

3. The problem this issue solves

The full pipeline has four stages, each of which will eventually be sophisticated. Building all four properly in one go would be a big, risky change. So this issue builds the whole pipeline with only the plumbing real: all four stages exist, run in order, and produce a valid Event. Two are honest placeholders.

1. classify placeholder ("stub"): later it will check the question for personal data or tricks
2. retrieve real: uses the retriever from #40
3. draft asks an AI model to write the answer from the retrieved Chunks (a simple prompt for now)
4. verify placeholder ("stub"): later it will score how well the answer is supported

You've done this before as a "walking skeleton" or tracer bullet: get a thin end-to-end slice working, then replace each fake part one at a time. Each later change swaps one function, and the pipeline keeps producing valid Events throughout.

4. The tool: LangGraph

The pipeline is built with LangGraph, a Python library for running a flowchart of steps. You describe three things:

  • State: a shared bag of data (question, retrieved Chunks, answer, list of Steps).
  • Nodes: plain functions. Each reads the state and returns only the bits it wants to change.
  • Edges: which node runs after which. Here it's a straight line.
Concept: it's a state machine

If you've hand-rolled state machines (as in your thesis work), this is the same thing: the state is the context, nodes are transitions, and what a node returns is a patch merged into the state. A straight line is the simplest case. Later, an edge can branch, for example "if nothing was retrieved, skip straight to the end."

Concept: reducers, or how updates merge

Normally a node's returned value overwrites that part of the state. That would be wrong for the list of Steps, because each node would erase the one before. So the list is marked to append instead (operator.add). Each node returns {"steps": [my_step]} and the list grows in run order. It's event-sourcing in miniature: nodes append facts and nothing edits an earlier one.

5. What the code does

Everything is in track-b/graph.py. There are two entry points:

  • build_graph(retriever, chat_model, draft_model_name, clock) wires up the four nodes and returns the runnable graph. The retriever, the chat model and the clock are passed in rather than hard-coded, so tests can swap them for fakes. This is dependency injection, as in .NET.
  • answer_question(graph, question) runs the graph and assembles the final Event: a fresh UUID, event_type: "QueryAnswered", no flags, and the Steps in order.

Each node records a Step describing itself: its name, which model it used, its cost, and how long it took.

StepModel recordedNotes
classify"stub"Does nothing yet.
retrievenomic-embed-textAlso saves each Chunk's id, document id, text and similarity score.
draftwhatever model is passed inSends the Chunk text plus the question to the chat model.
verify"stub"Confidence is 0.0.
Concept: placeholders say they're placeholders

An audit trail that records a placeholder as if it were a real judgment is worse than a gap. So the stubs are recorded under the model name "stub", and verify reports confidence 0.0, so nothing downstream can mistake it for a real score. (In this project, Confidence is always a score computed by verify, never the model's own claim about how sure it is.)

Concept: why retrieve saves the Chunk text, not just ids

The project has a feature called Replay: re-run an old question later and compare the new answer with the stored one. For that to be fair, the new run must see exactly the same passages as the original. The documents or chunking might change in the meantime, so the Step stores the actual text it retrieved.

Concept: timing with a monotonic clock

Latency is measured with time.perf_counter, a clock that only moves forward. The normal wall clock (datetime.now()) can jump (time sync, daylight saving) and give a negative or wrong duration. It's the same reason .NET has Stopwatch alongside DateTime.UtcNow. The clock is injectable, so a test can pass a fake clock and check exact timings.

Retrieve takes about 4.5 seconds, probably the first call loading the embedding model into memory. The stubs take microseconds. Cost is 0 everywhere because every model runs locally.

7. Testing without a real AI model

A real model gives different wording every time, so a test can't check "the answer equals X." Instead the tests use a scripted fake chat model (LangChain's FakeListChatModel): you give it the replies it should return, and it returns them in order. The graph is built exactly as in production, with only the model swapped at the edge. The same trick covers the retriever (a fake that returns fixed Chunks), so the tests need no database and no Ollama.

The tests check that the Event matches the shared JSON schema (schema/event.schema.json), that Steps come in order with the right cost and latency, that the stubs say "stub", and that retrieved Chunks are pinned with their text and score. The work was done test-first: write a failing test, then just enough code to pass it.

One extra rule: if the model returns a blank answer, draft raises an error. The schema requires a non-empty answer, so it's better to fail loudly at the step that caused the problem than to store a broken Event.

8. A gap left on purpose

If retrieval finds nothing, the graph still runs draft and verify. The project's rules say that situation should stop the pipeline and raise a no_chunks_retrieved flag. That is later work, and a comment at the top of graph.py says so, so it is a known gap rather than a hidden one.

9. Try it yourself

One test teaches the whole process

test_steps_run_in_order_with_zero_cost_and_measured_latency in track-b/tests/test_graph.py. It asks one question, runs the entire four-step pipeline (with a fake retriever, fake model and fake clock), then checks that the Steps came out as classify, retrieve, draft, verify, each costing 0 and taking 250 ms. From the repo root, with nothing else running:

python -m pytest track-b/tests/test_graph.py::test_steps_run_in_order_with_zero_cost_and_measured_latency -v

To see the Event the pipeline builds, add print(json.dumps(event, indent=2)) as the first line after event = _run() in that test and rerun with -s. You will see the same shape as the real run in section 6. Remove the print afterwards.

Why this one: the other tests each check a single rule (schema, "stub" names, pinned Chunks, blank answers). This one shows the pipeline running end to end, which is the whole point of the issue.

10. The whole thing in one paragraph

Issue #41 builds the complete question-to-Event pipeline as a LangGraph flowchart of four steps: classify, retrieve, draft, verify. Retrieve is real (from #40) and draft calls a model with a simple prompt. Classify and verify are labelled placeholders. Every step records its model, cost and timing, and the result is a valid Event. It lets every later improvement be a small swap into a pipeline that already works end to end.
