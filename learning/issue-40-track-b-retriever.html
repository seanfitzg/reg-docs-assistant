Issue #40, explained from the start

The "retrieve" half of the app: given a question, find the most relevant passages. No prior AI knowledge needed.

1. What is this project?

RegDocs Assistant answers questions about Irish financial-regulation documents, showing where in the real documents each answer came from. It's built in two parallel versions so you can compare approaches; Track B is the one using Python and the LangChain/LangGraph libraries. This issue creates Track B's folder and its first real component: the retriever.

Concept: RAG (Retrieval-Augmented Generation)

An AI language model (an "LLM") doesn't know your documents, and when it doesn't know something it tends to invent a plausible answer. RAG fixes this in two moves:

  1. Retrieve: search your documents for the few passages most relevant to the question.
  2. Generate: put those passages in the prompt and tell the model "answer using only these."

It's an open-book exam. This issue builds move 1 only.

Vocabulary (from CONTEXT.md): a Document is one regulatory publication, and a Chunk is one passage cut from it (a clause or numbered section) with a locator like "4.2" saying where it lives.

2. Where we were before this issue

Earlier issues (the /store folder) already did the hard preparation work:

  • Documents were split into Chunks and loaded into a Postgres database.
  • Each Chunk was turned into an embedding and stored in the database (explained next).
  • An eval harness (eval/run_eval.py) already ran a search query over those embeddings and measured how often the right passage was found. That measurement is saved as the "baseline run report".

What didn't exist was any Python folder for Track B, or a retriever that LangChain, the AI library, can plug into.

3. The key idea: embeddings

Concept: embeddings and vector search

A computer can't compare meanings directly, so an embedding model (here nomic-embed-text, running locally in Ollama) converts a piece of text into a long list of numbers, a vector. The model is trained so that texts with similar meaning get vectors that point in similar directions, even with no words in common. "How long must records be kept?" lands near "A firm must retain files for six years."

To search: embed the question, then ask the database for the stored Chunk vectors closest to it. A plain SQL LIKE or keyword search can't do that.

The database is Postgres with the pgvector extension. Its <=> operator measures cosine distance (the angle between two vectors; smaller means more similar). The code turns that into a similarity score with 1 - distance, so higher is better.

4. What was built

The Track B folder

A new track-b/ folder following the repo's per-folder conventions: its own Python virtual environment, requirements.txt, a README, pytest tests and Ruff formatting. A virtual environment is like a per-project NuGet package folder, so its dependencies don't leak into other projects.

The retriever: track-b/retriever.py

ChunkRetriever is a class that plugs into LangChain's standard retriever interface. You use it like this:

retriever = ChunkRetriever(embedding_client=client)   # k defaults to 5
documents = retriever.invoke("What must a firm disclose?")

Inside, invoke does three things:

  1. Embed the question with the same model used for the Chunks. It adds the prefix "search_query: " first. nomic-embed-text was trained with different prefixes for stored passages and for questions, and using the matching one gives better matches.
  2. Run one SQL query that finds the closest Chunk embeddings and returns the top k.
  3. Convert each database row into a LangChain Document: the Chunk's text becomes the content, and its details become metadata.

Each result looks like this:

Document(
  page_content = "Firms must act.",
  metadata = {
    "chunk_id": "c-1.1",
    "document_id": "doc-a",
    "locator": "1.1",
    "score": 0.83,
    "chunking_strategy": "clause_numbered"
  })

Three rules in the SQL

RuleHow
Top-k onlyORDER BY distance, LIMIT k. k is the number of passages returned. It's a setting, default 5 (DEFAULT_K), so it can be changed and recorded.
Only active ChunksA Document can be re-chunked with a new strategy, producing a new "Chunking Generation" while the old Chunks stay in the database (needed for Replay). The query joins on active_chunking_generation_id so old-generation Chunks can never be returned.
Stable orderTies in distance are broken by Chunk id, so results never shuffle between runs.

5. Key decisions

Decision: write our own retriever, not LangChain's PGVector (ADR-0032)

LangChain ships a ready-made Postgres vector store, but it creates and manages its own tables. Using it would mean copying every embedding into a second table or bending the existing schema to fit it, which clashes with earlier decisions (embeddings keyed by Chunk and model, only active Chunks searchable). It would also hide the search SQL, the part worth understanding. A custom retriever reuses the existing tables and the existing store/db.py and embedding client. Think of it as writing a thin adapter over your own repository rather than adopting an ORM that wants its own schema.

Decision: pure vector search, so the numbers must match the baseline (ADR-0030)

The search SQL is deliberately the same as the one the eval harness already used. That gives a strong check: run the new retriever over the eval questions and the results must match the saved baseline report. If they don't, the cause can only be a bug in the port, not a changed algorithm. Better searches (such as mixing in keyword search) come later and are measured separately.

Because downstream code only sees LangChain's retriever interface, a later hybrid retriever changes this one class.

The Postgres tests use a fake embedding client: it returns hand-made vectors (a "1" in one position, zeros elsewhere), so you can know exactly which Chunk should be closest without running a real model.

7. Try it yourself

Two tests teach the whole process
  1. test_row_becomes_document_with_chunk_text_and_metadata in test_retriever_mapping.py. It shows the shape of what the retriever hands to the rest of the app. No dependencies.
  2. test_inactive_generation_chunk_is_never_returned in test_retriever.py. It shows vector search in action: the query vector points straight at an old-generation Chunk, and the retriever still doesn't return it. This one needs the Postgres container running; it skips itself if it isn't.
python -m pytest track-b/tests/test_retriever_mapping.py::test_row_becomes_document_with_chunk_text_and_metadata -v
python -m pytest track-b/tests/test_retriever.py::test_inactive_generation_chunk_is_never_returned -v

To poke at them: in the first, change 0.83 in the row and watch the assertion fail on score. In the second, delete the AND documents.active_chunking_generation_id = ... line from RETRIEVAL_SQL in retriever.py and rerun, and c-old will appear in the results and fail the test. Undo the change afterwards.

Why these two: together they cover the two halves of the retriever, "what comes out" and "which Chunks are allowed to come out". The remaining tests are variations (top-k ordering, the default cap), and the parity test is a heavy full-dataset check.

8. The whole thing in one paragraph

Issue #40 creates the Track B Python project and a ChunkRetriever: it embeds the user's question, runs one SQL query against the existing embeddings to find the closest active Chunks (default 5), and returns them as LangChain Documents carrying the Chunk id, document id, locator and similarity score. It reuses the existing database and embedding code, and it is deliberately plain vector search so its results can be checked against the saved baseline. Issues #41 and #42 then plug it into the question-answering pipeline.
