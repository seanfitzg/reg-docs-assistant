The concepts

Concept: the prompt is how retrieval reaches the model

In RAG, "retrieval-augmented" is literal: the retrieved text is pasted into the prompt. The model has no access to your database. It sees one string made of instructions, the Chunk text and the question. Whatever the prompt contains is the model's entire world for that call, which is why the instruction "use only the excerpts below" matters, and why the Chunks are laid out as numbered blocks ([1] …, [2] …) in rank order, best match first.

Concept: cite by number, resolve by lookup (ADR-0010)

LLMs are unreliable at reproducing exact identifiers from memory. Ask one to write "section 7.1" and it will sometimes write a plausible "7.2". So the model is only asked for something easy and checkable: write the number of the excerpt that supports each claim. Code then does the part that must be exact:

marker 2  →  chunks[2 - 1]  →  { document_id: "doc-b", locator: "7.1" }

This is a database fact, not a model claim. A wrong number can only point at a Chunk that was genuinely retrieved, so every Citation shown is real. It's the same move as a foreign key: the model supplies a reference, and the system validates and dereferences it. A number that points at nothing ([0], or [9] when five Chunks came back) is dropped from the Citations and stripped from the stored answer, because an obviously missing citation is better than a plausible wrong one.

Concept: a prompt is a versioned artifact

The prompt lives in track-b/prompts/draft-v1.txt, not in a Python string. It's loaded when the graph is built, so a missing file fails at startup and not on the first user question. Changing the wording means a new file, draft-v2.txt, beside the old one. That fits the audit-trail goal: Replay (ADR-0005) deliberately runs the current prompt, and old versions stay readable so you can see what changed when answers drift. The plan's example Event even carries a prompt_version. The current Event schema has no such field, so the version is the file name for now.

Concept: why the real-model test is opt-in

The scripted fake model proves the graph resolves markers correctly. It can't prove a real model writes them. Only a real model can show that, and a real model is slow (a 7B model on CPU took about 85 s for one call here), needs 4.7 GB of weights, and isn't strictly deterministic. So that test runs only with RUN_REAL_DRAFT=1, with temperature=0 to make the output as repeatable as it gets. It's the same split as the parity test from #40: fast, offline tests by default, and slow checks against real components on demand.

What was built

What I did

prompts/draft-v1.txt (a template with {context} and {question}), and in graph.py a _draft_prompt that numbers the Chunks, plus _resolve_citations(answer, chunks). That function finds each [n] with a regex and substitutes it through a callback: an in-range marker stays in the text and becomes a Citation (once, however many times it's used), and an out-of-range one is removed. A Citation is {marker, chunk_id, document_id, locator} and lives in the graph's final state (final["citations"]). We agreed up front that the shared Event schema doesn't change, because it has no field for Citations, and they can be recomputed from the stored answer's markers and the pinned chunks. The test seam, also agreed, is the graph itself: graph.invoke and answer_question, with a scripted FakeListChatModel and a recording fake that captures the exact prompt sent.

A real model, run for real

qwen2.5:7b-instruct at temperature 0, with three hand-written Chunks (4.2 records, 7.1 fee-waiver notice, 9.3 complaints):

Q: How much notice must a firm give before applying a fee waiver?
A: A firm must give 30 days' written notice before applying a fee waiver. [2]
C: [(2, '7.1')]

Q: How long must records be kept and how fast must complaints be acknowledged?
A: Records must be kept for six years, and complaints must be acknowledged in five days. [1][3]
C: [(1, '4.2'), (3, '9.3')]

Q: What is the maximum penalty for a data breach?
A: The provided excerpts do not contain information regarding penalties for data
   breaches. Therefore, I cannot answer the question based on the given information. [1][2][3]
C: [(1, '4.2'), (2, '7.1'), (3, '9.3')]
Finding: the model refused, but still cited everything

The third question isn't in the excerpts. The model correctly declines, then adds [1][2][3] anyway, so the system faithfully resolves three Citations for an answer that says nothing the excerpts support. Resolution by lookup guarantees the Citations point at real retrieved Chunks. It doesn't guarantee those Chunks support the claim. That second guarantee is exactly the job of the verify Step (no_supporting_context), which is still a stub. This is the clearest reason verify exists, and nothing in this ticket should hide it.

What code review caught

Bug: an answer of only a bad marker became a blank answer

The blank-answer check from #41 ran before stripping. A model reply of just "[9]" passed the check, then stripping left "", which breaks the schema's non-empty answer. Found by reading the code, then pinned by a test that failed first. The check now runs after resolution.

Bug: a plausible first regex merged paragraphs

My first stripping regex was \s*\[(\d+)\], which "tidily" ate the whitespace before a bad marker. But \s includes newlines, so "First point [1].\n\n[9] Second point." lost its paragraph break and became "First point [1]. Second point.". The fix handles spaces and tabs only, never newlines. It also swallows the spacing on both sides of a marker that starts a line, so no stray leading space is left behind. Worth remembering: \s is rarely what you mean when only spaces are the target.

Smaller review fixes

Inline comprehensions in asserts moved into a named helper (a repo rule), a comment was rewrapped, and the duplicated "no usable answer" check was collapsed into one.

Known limits, deliberately left

Not handled

Grouped markers such as [1, 2] or [1-3] don't match the [n] pattern, so they stay in the answer text and produce no Citations. The prompt teaches [1][2] and the real model followed it, but a drifting model could write the grouped form. Legal text containing its own bracketed numbers (footnotes like [2]) is indistinguishable from a citation if the model echoes it. And a prompt template with literal braces would fail at question time rather than at startup. Each is a candidate for a later hardening ticket, not this one.
