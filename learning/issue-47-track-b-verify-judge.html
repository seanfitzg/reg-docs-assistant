Issue #47 — Checking the answer against its sources, and scoring how well it held up

The assistant's last pipeline step was a placeholder that always reported zero confidence. This issue replaces it with a real check: a second model reads the answer claim by claim and says which ones the retrieved passages actually support. Code turns those verdicts into a score and, when the score is poor, raises a warning flag. The answer is never changed or retried. Follows issue #46's writeup.

What the project is, and where we were

RegDocs Assistant answers questions about regulatory documents with a four-step pipeline: classify the question, retrieve relevant passages (Chunks), draft an answer that cites them, and verify it. The first three steps are real. The fourth was a stub: it recorded the model name "stub" and a confidence of 0.0 on every run, so the stored record said nothing true about the answer's quality.

The problem, and the core idea

A language model can write a confident, fluent, wrong answer. In a regulatory setting, "sounds right" is not enough: a person reviewing an answer needs to know how much of it is actually backed by the source text. The idea is to check the draft against the very passages it was written from, one claim at a time:

Answer:  "A firm must give 30 days' notice [1]. Fee waivers are capped at 2%."
Passage: "A firm must give 30 days' written notice before applying a fee waiver."

Judge:   SUPPORTED:   A firm must give 30 days' notice.
         UNSUPPORTED: Fee waivers are capped at 2%.

Confidence = supported / total = 1 / 2 = 0.5   -> low_confidence
Concept: LLM-as-judge

Using one language model to grade another model's output is called LLM-as-judge. It is attractive because the checking task ("does this text support that claim?") is easier than the writing task, and because it scales. It is also imperfect: the judge is a model too, so it can be wrong, it can be fooled, and a model judging its own kind of output tends to be too kind to it. That is why the result here is a signal for a human to look at, never a guarantee, and why the repo's roadmap measures judges against human labels with evals.

Concept: why code computes the score, not the model

You could ask the model "how confident are you, from 0 to 1?" Don't. Models are poorly calibrated: a 0.9 from a model does not mean it is right nine times in ten. Instead the model only supplies simple, checkable facts (one verdict per claim) and ordinary code does the arithmetic. That keeps the score reproducible, testable with scripted replies, and comparable over time. It is the same principle as citations in issue #42: let the model do what it is good at (reading), and let code do the part that must be exact (resolving, counting).

Concept: annotate, never retry (ADR-0006)

When the check finds a weak answer, the obvious move is "ask the drafting model to try again until the judge is happy". The project deliberately does not. That loop would quietly steer the pipeline toward whatever the judge approves, which is a worse failure for a compliance tool than an honestly flagged, possibly weak answer that a human can see and override. So verify only annotates: the answer goes out exactly as drafted, with flags, and every step runs once.

What the code now does

The judge prompt and the format (prompts/verify-v1.txt)

The prompt gives the model the answer and the numbered passages and asks for one line per claim in exactly the format SUPPORTED: <claim> or UNSUPPORTED: <claim>. Like the other prompts it is a versioned file, so a change is a new file beside the old one.

Reading and scoring (judge.py)

FunctionJob
parse_verdictsReads those lines with a regular expression. It forgives bullets, numbering and capitals, because small models rarely follow a format to the letter. Anything that isn't a claim line is ignored.
confidence_ofSupported claims divided by all claims. No claims at all gives 0.0.
flags_forBelow LOW_CONFIDENCE_THRESHOLD (0.8) raises low_confidence. Exactly 0.0 also raises no_supporting_context.

A reply with no readable claim lines scores 0.0 and raises both flags. This is "fail closed" again, as in issue #46: a check that couldn't run must not look like a check that passed.

Before and after

Before: every Event's verify Step: {"model": "stub", "confidence": 0.0}, no flags ever raised.
After: {"model": "qwen2.5:7b-instruct", "confidence": 0.5} with "low_confidence" in the Event's flags, for the half-supported example above.

In the graph (graph.py)

The verify node formats the prompt, calls the injected judge model, and passes the reply through those three functions. Like the draft and classifier models, the judge is passed into build_graph with its name, so tests script it and production uses the real local model. By default it is the same Ollama model that drafts. Setting the JUDGE_MODEL environment variable to another Ollama model name (for example JUDGE_MODEL=llama3.1:8b before starting the API) makes a different model judge the drafter, which is generally better practice than a model grading itself. The Step then records that model's name. Which judge is actually best is a question for evals.

Try it yourself

1. The scoring rules, no dependencies: test_flags_follow_the_threshold_and_zero_support in track-b/tests/test_judge.py.

python -m pytest track-b/tests/test_judge.py::test_flags_follow_the_threshold_and_zero_support

It is a table of confidence values and the flags each should produce. Change the threshold constant in judge.py from 0.8 to 0.6 and watch the 0.75 row fail: that is how a single number changes which answers get flagged. This is the number you would tune with evals.

2. The whole step through the graph: test_partial_support_raises_low_confidence_only_and_keeps_the_answer in track-b/tests/test_graph_verify.py.

python -m pytest track-b/tests/test_graph_verify.py::test_partial_support_raises_low_confidence_only_and_keeps_the_answer

A scripted fake judge replies with one supported and one unsupported line. The test checks the flag and, importantly, that the answer comes back unchanged. Edit the scripted reply (HALF_SUPPORTED at the top of the file) to add a third supported line and see Confidence move to about 0.67 and still be flagged.

3. The real model, opt-in: test_the_real_judge_writes_claim_lines_that_code_can_read in track-b/tests/test_real_judge.py (needs Ollama with qwen2.5:7b-instruct).

RUN_REAL_JUDGE=1 python -m pytest track-b/tests/test_real_judge.py

This is the only test that shows a real model actually follows the line format; if it ever replied in prose, Confidence would be 0.0 and the test would fail. Temporarily print the Event to see the real judge's score for the example answer.

The first isolates the scoring logic, the second shows the pipeline behaviour (annotate, don't change), the third is the only contact with a real model. The other tests (parser edge cases, unreadable reply, prompt contents, no retries) vary these.

Summary. verify is now real. A judge model lists the answer's claims and marks each supported or unsupported against the retrieved Chunks in a strict line format. Code parses those lines, computes Confidence as the supported fraction, raises low_confidence below 0.8 and no_supporting_context when nothing is supported, and treats an unreadable reply as unverified. The Step records the real model name, the answer is returned untouched, and nothing is retried. The score is a signal for human review, not a guarantee, and its quality is not yet measured.
