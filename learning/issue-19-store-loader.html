Issue #19 — /store's loader

Getting ingestion's JSON output actually into Postgres. A sequel to issue #18's writeup — that one built the schema; this one populates it.

Where this fits

ingestion/output/*.json → loader.py (this ticket) /store's Postgres → (later) retrieval / RAG

#18 stood up an empty, correctly-constrained database. This ticket writes store/loader.py: a standalone Python script that reads the Document/Chunk JSON ingestion already produced and writes it into that schema. Run against the real corpus, it loaded 20 Documents, 20 Chunking Generations, 1993 Chunks — every Document ended up with its active_chunking_generation_id set, and re-running it a second time changed nothing (same row counts, no errors) — the "safe to re-run" requirement, actually proven, not just asserted.

A gap the spec got wrong: where does chunking_strategy come from?

The problem

The ticket assumed the loader could derive every chunking_generations row — including its chunking_strategy column — purely from the Chunk JSON files already sitting in ingestion/output. That's true for id and document_id (every Chunk carries chunking_generation_id and document_id), but not for chunking_strategy — it was never written into ingestion/output at all. Checking the actual JSON schemas confirmed it: Chunk only has id, document_id, chunking_generation_id, locator, text. Document doesn't have it either. The strategy name exists in exactly one place: ingestion/manifest.json, keyed by PDF filename — a deliberate earlier design decision (ADR-0014), not an oversight in ingestion.

The fix

loader.py reads manifest.json too, as a second input alongside ingestion/output. To match a manifest entry (keyed by filename, e.g. "01-cp01-funding-of-ifsra.pdf") up with a Document id ("doc-01-cp01-funding-of-ifsra"), the loader has its own one-line copy of the same rule ingestion/ids.py already uses — duplicated deliberately rather than importing across /ingestion and /store's independent Python environments, which would couple two folders meant to stay separately runnable (ADR-0020).

This isn't a change to ingestion — no code there moved — just an extra file the loader also reads.

The circular reference, again — this time in application code

Issue #18's writeup covered a circular foreign key at the schema level: documents.active_chunking_generation_id points at a Chunking Generation, whose own document_id points back at the Document. The exact same shape shows up again here, but now it's the loader that has to respect it when deciding what order to insert rows in — you can't insert a Document with its active_chunking_generation_id already set if that Generation doesn't exist in the database yet, and you can't insert a Generation if its Document doesn't exist yet either.

The fix: four phases, same idea as the schema's two-step ALTER TABLE

The loader writes in this order, all inside one database transaction:

PhaseWhatWhy it works
1Insert/update every document row — except supersedes and active_chunking_generation_id, left NULLNothing else needs to exist yet — these are the table's own primary keys
2Insert/update every chunking_generations rowEvery document_id it references was just created in phase 1
3Go back and UPDATE each Document's supersedes (only if the Document is new this run) and active_chunking_generation_id (every run)Every Document and every Generation now exists, so both circular references can finally be set — see below for why the two fields are treated differently
4Insert/update every chunk rowBoth its foreign keys (Document, Generation) already exist

Upsert: writing rows that might already exist

Concept

An upsert ("update or insert") writes a row if its key doesn't exist yet, or does something else if it does — one statement covering both cases, instead of the application first checking "does this exist?" and branching. Postgres's spelling is INSERT ... ON CONFLICT (key) DO .... The "something else" is usually DO UPDATE SET ... (overwrite the existing row with the new values), but this loader uses DO NOTHING instead: 

INSERT INTO chunking_generations (id, document_id, chunking_strategy)
VALUES (%(id)s, %(document_id)s, %(chunking_strategy)s)
ON CONFLICT (id) DO NOTHING

DO UPDATE SET col = EXCLUDED.col would be the more commonly-reached-for form (EXCLUDED is Postgres's name, inside a DO UPDATE clause, for the row that would have been inserted — the nearest T-SQL equivalent is MERGE). It's not what this loader uses, and that was actually a bug caught on the first pass of /code-review, covered below.

Upsert-by-id is why this loader can be run over and over — after ingestion re-processes a document, after a schema tweak, whenever — without ever needing a "wipe everything and start over" step. That matters specifically because documents, chunking_generations, and chunks are all immutable once written (CONTEXT.md, and ADR-0021 for Chunking Generation specifically): a truncate-and-reload loader would be simpler to write, but would destroy every earlier Generation on every run, which breaks Replay (re-running a past query's exact original context) the moment more than one Generation of the same Document exists.

Given that immutability, DO NOTHING is actually the philosophically correct choice, not just a simpler one: if a row's id already exists, nothing about its content is supposed to change — a real correction is meant to arrive as a brand new Document (linked via supersedes), never a silent edit to the old one. created_at on chunking_generations benefits from the same idea a different way: it's left out of the insert's column list entirely, so the column's own DEFAULT now() fills it in once, on the row's actual first insert, and re-running the loader a year later can never silently rewrite when a Generation was really first created.

One transaction, not one statement per row

Concept

with psycopg.connect(db_url) as conn: wraps the entire load — all four phases, every row — in a single database transaction. On a clean exit it commits everything at once; if anything raises partway through, everything rolls back and the exception propagates up as a normal Python traceback. The closest .NET analogy is a using var transaction = connection.BeginTransaction() wrapping the whole unit of work, except psycopg's connection context manager commits/rolls back for you automatically based on whether an exception escaped the block.

This is why "a loader failure surfaces loudly" (an acceptance criterion) needed no special error-handling code at all — an uncaught exception already does exactly that, and the transaction wrapper means it can never leave the database half-updated on the way out.

This is a deliberate contrast with ingestion's own per-document failure isolation (ADR-0019), where one corrupt PDF is expected, ordinary input and shouldn't take down the whole batch. Here, a failure would mean already-validated JSON somehow doesn't fit the schema — a bug worth stopping the whole run over, not skipping past.

What two rounds of /code-review actually caught

This ticket went through /code-review twice — the first pass on the initial implementation, a second pass after fixing everything the first one found. Both surfaced real, not-cosmetic bugs, worth walking through rather than glossing over:

Round 1: tests could destroy real data

The first version of the tests wiped every row in documents/chunking_generations/chunks before and after each test — against the same local database store/README.md tells you to load the real 20-document corpus into. Follow the README top to bottom (bring the container up, load the real corpus, then run the tests) and the test suite would silently delete everything just loaded, with no warning anywhere.

Fix: a second database, regdocs_test, created automatically alongside regdocs (store/init/002_test_database.sql — schema-identical, via psql's \c/\i meta-commands re-running 001_schema.sql against the new database). Tests now default to regdocs_test; the real regdocs database is never in their reach at all, not just "cleaned up carefully."

Round 2: "upsert" was quietly rewriting immutable history

The original chunking_generations upsert used DO UPDATE SET chunking_strategy = EXCLUDED.chunking_strategy. Since chunking_strategy is looked up fresh from manifest.json on every call, re-running the loader after a manifest edit would silently overwrite an already-loaded, supposedly-immutable Generation's recorded strategy — corrupting exactly the kind of historical fact Replay depends on staying accurate. The same shape of bug existed for documents.supersedes: phase 3's UPDATE set it unconditionally on every run, not just a Document's first load.

Fix: switched every upsert to ON CONFLICT DO NOTHING (covered above), and made phase 3 check which Documents were already loaded before writing anything, so supersedes is only ever set the first time — the same "original row wins" rule the rest of the loader already followed, now applied consistently everywhere.

A handful of smaller findings from both rounds are in the commit history too: clearer errors (a plain Python ValueError naming the actual problem) in place of raw database errors for drift between ingestion/output and manifest.json, a closed-set check on chunking_strategy before it ever reaches the database, and a check that two Chunks can't disagree about which Document their shared Chunking Generation belongs to.

How it was tested

Same seam-and-skip-pattern conventions as #18's writeup covered, applied to the loader specifically — six tests total, all against regdocs_test:

Verified
  • A synthetic fixture — one Document, deliberately re-chunked into two Chunking Generations — proves upsert-by-id doesn't collide or overwrite chunks across Generations of the same Document. (The real corpus only has one Generation per Document so far, so this scenario only exists as a fixture.)
  • Running the loader twice against the same fixture leaves row counts unchanged — the actual idempotency check, not just an assertion that it "should" be safe.
  • Two direct regression tests for the round-2 bugs above: re-running with a changed manifest doesn't touch an existing Generation's chunking_strategy, and re-running with a changed supersedes value doesn't touch a Document's original link.
  • An invalid chunking_strategy value raises a clear ValueError naming the bad value, rather than a Postgres error from deep inside a batch insert.
  • A test runs the loader against the real, full ingestion/output (skipped if that folder isn't present locally, since it's not committed to git) and checks the row counts match what's on disk, and that no Document was left with a NULL active Generation.
  • All Postgres-dependent tests are decorated with a reachability check that skips (not fails) if docker compose up hasn't been run — the same convention ingestion/tests uses for missing corpus PDFs.

What's next

With both #18 and #19 done, /store is a real, populated, queryable database of every ingested Document and Chunk.
