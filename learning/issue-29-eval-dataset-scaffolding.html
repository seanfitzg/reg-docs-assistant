Issue #29 — Scaffolding the retrieval eval set

The first piece of /eval: a schema for hand-written Eval Cases, a test that every label points at something real, and a keyword-search helper for writing them. No retrieval yet. This ticket prepares the measuring stick, and the thing it measures comes later. Follows issue #25's writeup.

Where this fits

#29 schema + checks + helper → #31 you write 15–20 cases → #32 harness + baseline ← #30 match rule

Epic #28 exists because /store now has a vector for every active Chunk, but there's no way to tell whether searching those vectors returns the right Chunks. The design was settled in a grilling session and recorded as ADR-0027 to ADR-0030 before any code. This ticket builds only the scaffolding: schema/eval-dataset.schema.json, an empty eval/dataset.json, the checks that keep it honest, and eval/find_locator.py. It's verified by 8 new schema-fixture tests and 20 /eval tests. The full suite passes across all four folders (154 tests).

The PR touches 29 files, but only five hold real logic. The rest are tests, test data and docs. A tour of the files goes through every one of them: what it is, why it exists, and how it connects to the others.

The concepts

Concept: a retrieval eval is a labelled test set

Each Eval Case is a question plus the place its answer lives. Later (#32) the harness runs every question through retrieval and asks: is the right place among the top k results, and how high? Two standard metrics come out of that. Recall@k is the fraction of questions whose answer appears in the top k. MRR (mean reciprocal rank) averages 1/rank: first place scores 1, third place scores ⅓, a miss scores 0.

The closest analogy is a BDD suite for search: Given this question, then this passage comes back. Unlike most "AI evals", nothing here needs a model to grade it. The check is a deterministic comparison, which is why it can run on every change the way unit tests do. Judging the quality of a drafted answer is a different and harder problem (LLM-as-judge), and it comes much later.

Concept: why the label is a locator, not a Chunk id (ADR-0027)

Chunk ids are regenerated every time a Document is re-chunked (ADR-0003). One of the eval's jobs is to compare chunking strategies, so labels that break on every re-chunk would make that job impossible. A Gold Locator is (document_id, locator), e.g. ("doc-04-cp54-…", "3.12"). It names a place in the Document's own structure, which stays the same whatever the chunker does. The cost is that "did retrieval find it?" is no longer a simple equality check. It needs a match rule, and that rule is #30.

Concept: lexical overlap bias, and why every case is tagged (ADR-0029)

When you write a question while looking at the passage, you echo its wording. Retrieval then scores well because it's matching words you copied, not because it understood anything. Real users don't know a regulation's vocabulary. So every case carries phrasing: lexical | paraphrase, and recall is reported for each group. The gap between the two numbers is itself a finding: it shows how much the embedding model understands meaning and how much it matches words. This is also why the cases are hand-written and not LLM-drafted, since generated questions echo their source even more strongly.

Concept: keyword search vs. embedding search

find_locator.py is deliberately plain lexical search. A Chunk matches if every word appears in it, ignoring case. That's what you want when you already know roughly what the passage says and need its exact locator. It's also the opposite of what #32 will do: embed the question and find the nearest vectors, matching on meaning. Running the same question through both is the quickest way to see what "semantic search" actually adds, and where it misses things plain keywords would find.

Concept: two checks that look alike but answer different questions

check_dataset.find_problems compares locators by exact string equality. #30's match rule will not be exact: 3.12(a) will count as a hit for 3.12. That isn't a contradiction. The exact check answers "is this label a typo?", and the match rule answers "would retrieval count this as a hit?". If they were merged, a mistyped label like 3.2 for 3.12 would look like a retrieval miss on every run, forever, and the lower score would be blamed on the model.

Group 1: the contract (schema/)

schema/eval-dataset.schema.json

A JSON Schema: a JSON file that describes the allowed shape of another JSON file. It plays the same role as an XSD for XML, or the [Required]/[RegularExpression] attributes on a C# DTO: it's the rules, written as data, and any language's validator can enforce them. It lives in /schema next to chunk.schema.json and the rest because it's a shared contract. A later .NET harness can validate the same file against the same rules (ADR-0011).

The top level says a dataset is { "dataset_version": <integer ≥ 1>, "cases": [ <evalCase>, … ] }, with no other keys allowed ("additionalProperties": false). The two reusable shapes are declared once under $defs and referenced with $ref, much like declaring a class once and using it as a property type in several places:

"$defs": {
  "goldLocator": { document_id: string, locator: string }           // used by gold_locators AND superseded_locators
  "evalCase":    { id: "q01"-style, question, phrasing: lexical|paraphrase,
                   category: single_passage|multi_locator|supersession|unanswerable,
                   gold_locators: [goldLocator], superseded_locators?: [goldLocator],
                   answer_quote?: string, notes?: string }
}                                                                   // (simplified; the real file is JSON Schema syntax)

The one tricky part, where required fields change by category, is covered in the next section.

schema/fixtures/eval-dataset/*.json (8 files)

Example datasets for testing the schema itself. Two are valid-* and must pass: valid-empty-seed.json (the empty starting point) and valid-mixed-categories.json (one case of each awkward shape). Six are invalid-*. Each is a valid dataset with exactly one rule broken, and its filename says which one. This is the same fixture convention /schema already uses for Documents and Chunks.

schema/tests/test_eval_dataset.py

Two tests, each run once per fixture file. @pytest.mark.parametrize is the Python equivalent of nUnit's [TestCase(...)]: one test method, many inputs, each reported as its own test.

@pytest.mark.parametrize("fixture_name", ["valid-mixed-categories.json", "valid-empty-seed.json"])
def test_valid_dataset_passes_validation(fixture_name):
    validate(load_json(FIXTURES / fixture_name), load_json(EVAL_DATASET_SCHEMA))

@pytest.mark.parametrize("fixture_name", ["invalid-unanswerable-with-gold-locators.json", ...])
def test_invalid_dataset_fails_validation(fixture_name):
    with pytest.raises(jsonschema.exceptions.ValidationError):     # like Assert.Throws<T>
        validate(load_json(FIXTURES / fixture_name), load_json(EVAL_DATASET_SCHEMA))

So this file tests the schema, not your dataset. Your dataset is tested in eval/tests/test_dataset.py.

Group 2: the tools (eval/)

eval/dataset.json

The Eval Cases themselves, and the only file in this PR you'll edit by hand (in #31). It's empty for now:

{ "dataset_version": 1, "cases": [] }

A filled-in case looks like the example in eval/README.md. Bump dataset_version whenever you change the cases, so every future eval run report records which version of the questions it used (ADR-0030).

eval/corpus.py: one function, load_active_chunks()

Reads the ingested corpus from ingestion/output/, the JSON files the ingestion pipeline writes. There are two kinds: documents/*.json (one object per Document, including its active_chunking_generation_id) and chunks/*.json (one array of Chunks per Document, which can include Chunks from older generations). The function returns only the Chunks from each Document's active generation, because those are the only ones retrieval ever searches, so they're the only ones a Gold Locator may point at.

documents = [json.loads(p.read_text(...)) for p in sorted((output_dir / "documents").glob("*.json"))]
active_generation = {d["id"]: d["active_chunking_generation_id"] for d in documents}   # doc id → active gen

for path in sorted((output_dir / "chunks").glob("*.json")):
    for chunk in json.loads(path.read_text(...)):
        if active_generation.get(chunk["document_id"]) == chunk["chunking_generation_id"]:
            chunks.append(chunk)                                                          # keep active only

In LINQ terms: build a Dictionary from the documents, then a Where over all Chunks that keeps those whose generation equals their Document's active one. It reads files, not Postgres, so writing cases never needs Docker running.

eval/check_dataset.py: one function, find_problems(dataset, active_chunks)

The checks a JSON Schema can't express, because they need more than the file's own shape. A schema can check that a locator is a non-empty string. It can't check that the string actually exists in the corpus. It also can't check that ids are unique across all cases.

existing = {(c["document_id"], c["locator"]) for c in active_chunks}   # a HashSet of (doc, locator) pairs

for case in dataset["cases"]:
    if case["id"] in seen_ids:  problems.append(f"duplicate case id: {case['id']}")
    for entry in case["gold_locators"] (and superseded_locators):
        if (entry["document_id"], entry["locator"]) not in existing:
            problems.append(f"{case_id}: gold locator not found in active Chunks: {doc} / {locator}")
return problems                                                           # [] means all good

It returns a list of messages rather than raising on the first problem, so one test run shows you every typo at once. It's also a pure function: data in, list out, no file reading. That's why it can be tested with tiny hand-made inputs (see Group 3).

eval/find_locator.py: search() plus a command-line main()

Your lookup tool while writing cases. It has two layers, the same split as check_dataset:

  • search(chunks, terms, document_id=None), the pure logic. It returns a KeywordMatch(document_id, locator, snippet) for every Chunk containing all the words, ignoring case. KeywordMatch is a @dataclass(frozen=True), Python's nearest thing to a C# record.
  • main(argv), the thin command-line wrapper. It parses arguments with argparse (like System.CommandLine), rejects blank terms and unknown --doc ids, calls corpus.load_active_chunks() then search(), and prints the results:
$ python eval/find_locator.py "fitness probity" --doc doc-10-cp160-fitness-and-probity-regime
doc-10-cp160-fitness-and-probity-regime  |  Chapter 4: Questions (p. 15)
    ...the application of fitness and probity standards and other governance related requirements...
9 match(es)

The part before | is what you copy into document_id, and the part after it is the locator. The if __name__ == "__main__": guard at the bottom means main() only runs when you execute the file directly, not when a test imports it. It's the Python equivalent of a Program.Main that tests never trigger.

eval/requirements.txt and eval/README.md

requirements.txt is this folder's dependency list, roughly a .csproj's <PackageReference>s: jsonschema[format] and pytest. Like /schema, /ingestion and /store, /eval gets its own virtual environment (eval/.venv, gitignored), so its packages never clash with another folder's. The README covers setup, how to write cases, and how to run the tests.

eval/tests/test_check_dataset.py (7 tests)

Tests corpus.load_active_chunks() (only 1.1, 3.12 and Introduction (p. 3) come back, never 9.9) and check_dataset.find_problems(). The find_problems tests all follow one pattern: load the known-good dataset, break exactly one thing, and assert the exact message:

def test_missing_gold_locator_is_reported_with_case_id_and_locator():
    dataset = _valid_dataset()
    dataset["cases"][0]["gold_locators"][0]["locator"] = "3.2"      # a plausible typo for "3.12"

    problems = find_problems(dataset, load_active_chunks(FIXTURE_OUTPUT))

    assert problems == ["q01: gold locator not found in active Chunks: doc-a / 3.2"]

The other broken variants are: a duplicate id, a locator that only exists in the inactive generation (9.9), the right locator under the wrong Document, and a bad superseded_locators entry. It's the "valid object, then mutate one field" style you'd use with a test-data builder in C#.

eval/tests/test_find_locator.py (10 tests)

Tests search():

  • matching ignores case
  • every word must appear, but not next to each other (so the line break in 1.1 doesn't matter)
  • inactive Chunks are never returned
  • --doc filtering works
  • snippets have their whitespace flattened
  • no match returns an empty list
  • blank terms are rejected

It also tests main(): blank terms exit with argparse's usage-error code 2, and an unknown --doc is reported. main() accepts an --output-dir, so these tests point it at the miniature corpus rather than the real one.

eval/tests/test_dataset.py (3 tests): your safety net

The only test that reads your eval/dataset.json. It does two things:

  • test_dataset_matches_schema validates the real dataset against eval-dataset.schema.json. It also validates fixtures/valid-dataset.json, so if the schema tightens later, the unit tests can't keep quietly testing a dataset shape the real file could no longer have.
  • test_dataset_has_no_duplicate_ids_or_missing_locators runs find_problems() against the real corpus and prints every problem at once if it fails. It carries a @requires_ingestion_output marker, so on a fresh clone where ingestion/output/ doesn't exist yet (it's gitignored) it's skipped with a reason rather than failing. That's the same pattern as requires_cp54 in /ingestion and requires_postgres in /store.

Concept: why three small files instead of one script

All of /eval could have been one script that reads files, checks, searches and prints. It's split so that the logic (find_problems, search) is pure, taking data in and giving data out, while the messy parts sit at the edges: file reading in corpus.py, and argument parsing and printing in main(). This is sometimes called functional core, imperative shell. The payoff is visible in Group 3: the core is tested with a 4-file fake corpus in milliseconds, and only one test touches the real world. It's the same reason you'd keep a C# domain service free of File.ReadAllText and Console.WriteLine. #32's harness will reuse corpus.py and follow the same split.

The schema: JSON Schema's if/then/else

Most of the schema is ordinary: required fields, closed enums for phrasing and category, and a q01-style id pattern. The interesting part is that which fields are required depends on the category. JSON Schema expresses that with conditionals, which you can read as a switch over one field with a different shape for each branch:

"allOf": [
  { "if":   { "properties": { "category": { "const": "unanswerable" } }, "required": ["category"] },
    "then": { "properties": { "gold_locators": { "maxItems": 0 } }, "not": { "required": ["answer_quote"] } },
    "else": { "properties": { "gold_locators": { "minItems": 1 } }, "required": ["answer_quote"] } },
  { "if":   { "properties": { "category": { "const": "supersession" } }, "required": ["category"] },
    "then": { "required": ["superseded_locators"] },
    "else": { "not": { "required": ["superseded_locators"] } } }
]

Two details in there are easy to miss. The "required": ["category"] inside each if matters because an if on a missing property passes vacuously, so without it a case with no category would be treated as unanswerable. And "not": { "required": [...] } is how JSON Schema says a field is forbidden. There's no forbidden keyword, so you negate "required".

Caught while building

Garbled quotes that looked like bad data

The first real search printed � where the PDFs have bullets and curly quotes. It looked like broken extraction, but a byte search of ingestion/output found no replacement characters, so the data was fine. The cause: when Python's output on Windows goes to a pipe rather than a live console, it's encoded in the legacy cp1252 code page, and the terminal decoded those bytes as UTF-8. This matters more here than it would elsewhere, because answer_quote text gets copied straight out of this tool's output. Fix: sys.stdout.reconfigure(encoding="utf-8") at the start of main().

What /code-review caught

Bug: blank search terms crashed — "vacuous truth"

The spec reviewer ran find_locator.py " " and got an IndexError. The chain of events:

wanted = [t.lower() for t in "   ".split()]   # [] -- split() drops empty strings
all(term in lowered for term in wanted)        # True! nothing in [] failed the test
start = lowered.find(wanted[0])                # IndexError: list index out of range

all() over an empty sequence is True, just as LINQ's new int[0].All(x => false) is true. Logicians call this vacuous truth. So an empty filter matched every Chunk, and the crash only happened one line later. The fix: search() raises ValueError for blank terms, and main() turns that into a proper argparse usage error (exit code 2) instead of a traceback. The failing test came first and was red with that same IndexError. The general lesson is that any "every item must pass" filter needs a decision about what an empty filter means.

Standards review: fixed
  • Two comments described the wrong code. In corpus.py, the "dict comprehension" comment sat above a list comprehension. A test comment claimed a set of locators was built, but the code built (document_id, locator) pairs, and the variable was misleadingly named locators.
  • Hit → KeywordMatch. In CONTEXT.md a "hit" means a retrieved Chunk matching a Gold Locator under ADR-0028's rule. Reusing the word for a keyword result would blur two ideas that #32 will need to keep apart.
  • A mistyped --doc printed "0 match(es)", which reads as "not in this Document". It now says the Document id doesn't exist.
  • Fixture renamed to valid-dataset.json to follow the valid-*/invalid-* convention. A missing encoding="utf-8" was added. Comments were added for the remaining unfamiliar idioms: [match] = … destructuring (which also asserts exactly one result), tuple unpacking in for, file=sys.stderr, the _ "private by convention" prefix, and why main(argv=None) is injectable.
Judgement calls left as they are

test_dataset.py repeats one line of schema/tests/support.py's format-checker setup rather than importing it, because sharing it would link two separate venvs for one line. The (document_id, locator) pair still has no type of its own, which fits better in #30, where the match rule actually operates on it. "Passage" appears in prose even though the glossary tells Chunk not to use it: there it means the source text, not a Chunk, and it's the ADRs' own wording.

One decision is open for you: the spec called superseded_locators "optional", but the schema requires it for supersession cases and forbids it elsewhere. Without it, a supersession case would be indistinguishable from a single-passage one.
