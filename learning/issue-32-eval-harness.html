Issue #32 — The retrieval eval harness and the first baseline

The harness that turns the eval set into numbers. It embeds every question, runs a nearest-neighbour search in pgvector, grades what comes back with the #30 match rule, and writes an immutable run report. It was built test-first against hand-made vectors, then run for real. The first result: Recall@10 = 0.89 and MRR = 0.75, with a clear gap between lexical and paraphrase questions. Follows issue #30's writeup.

Where this fits

#29 schema + checks → #30 match rule → #31 the 20 cases → #32 harness + baseline → .NET retriever must match it

Everything before this ticket was preparation. The store holds 1,993 Chunks, each with an embedding from nomic-embed-text (#25). The eval set holds 20 questions labelled with where their answers live (#31), and the match rule can grade a retrieved Chunk against a label (#30). This ticket joins them up: eval/run_eval.py asks the store every question and turns the answers into a score. That score is the baseline, the number every later change gets compared with, starting with the Week-2 .NET retriever.

The concepts

Concept: nearest-neighbour search, and cosine similarity

An embedding is a list of 768 numbers, which you can think of as a direction in a 768-dimensional space. The model was trained so that texts with similar meaning point in similar directions. Retrieval is then pure geometry: embed the question, and find the stored Chunk vectors that point most nearly the same way. That's nearest-neighbour search.

"Most nearly the same way" is measured with cosine similarity, the cosine of the angle between two vectors. Pointing the same way gives 1, at right angles (unrelated) gives 0, and opposite gives −1. It ignores vector length and looks only at direction, which is where these models encode meaning. pgvector's <=> operator returns cosine distance, which is 1 − similarity, so the query sorts by distance and reports 1 − distance:

ORDER BY chunk_embeddings.embedding <=> %(query)s::vector   -- smallest distance first
LIMIT 10                                                     -- the "top-k", k = 10

In .NET terms it's chunks.OrderBy(c => Distance(c.Vector, q)).Take(10). The database does the OrderBy, because computing 1,993 distances is its job and not something to drag into application code.

Concept: exact search vs. an approximate index

With no index, Postgres computes the distance to every row and sorts them, which is an exact search. At ~2,000 rows that takes milliseconds. Vector indexes (ivfflat, hnsw) get their speed by searching only part of the space, so they can miss a true nearest neighbour. That's why they're called approximate nearest-neighbour (ANN) indexes. For a measurement that's a problem: a missed case might be the embedding model's fault or the index's, and you couldn't tell which. So the issue deliberately says no index. Add one when the corpus is big enough to need it, and measure the recall it costs by running this harness with and without it.

Concept: the query half of the asymmetric prefix (ADR-0026)

nomic-embed-text was trained to embed stored documents and search queries slightly differently, and it's told which is which by a text prefix. #25 embedded every Chunk as "search_document: <text>". This harness sends every question as "search_query: <question>". Leave the prefix off and nothing breaks: vectors still come back and results still look sensible. The scores just quietly get worse. That's the worst kind of bug, and it's why the test asserts the exact string sent to the model, and why the report pins the prefix. If the .NET retriever later scores lower on the same embeddings, a missing prefix is the first thing to check.

Concept: Recall@k and MRR, the two scores

For each answerable question, the harness records the rank of the first retrieved Chunk that's a hit (1 = top result), or "miss" if none of the 10 is.

Recall@k is the fraction of questions whose first hit is within the top k. Recall@3 = 0.83 means "for 83% of questions, a right Chunk was in the top 3". It's easy to read, but it can't see where inside those k results the hit landed.

MRR (Mean Reciprocal Rank) averages 1/rank, with a miss counting as 0. Rank 1 scores 1.0, rank 2 scores 0.5, rank 4 scores 0.25. It rewards putting the right Chunk first, which matters because the LLM that eventually answers is given only the top few Chunks, and reads the first one most carefully. A worked example, from the fixture test:

ranks:     q01 = 1      q02 = 3      q03 = miss

Recall@1  = 1/3               (only q01 is in the top 1)
Recall@3  = 2/3               (q01 and q02)
MRR       = (1/1 + 1/3 + 0) / 3 = 4/9 ≈ 0.44

These are the retrieval equivalents of the coverage numbers from a test suite: aggregate numbers that are only meaningful when compared with a previous run.

Concept: unanswerable questions have no recall, only a confidence

Vector search always returns its 10 nearest neighbours. There's no "0 results", because something is always nearest. So an unanswerable question can't hit or miss. Counting it as a miss would drag recall down for the wrong reason, which is why ADR-0029 excludes these cases from every metric. What the harness records instead is the top-1 similarity: how confident the best wrong match looked. That number is the raw material for a future similarity threshold ("below 0.7, say the corpus doesn't cover it"). The baseline shows why picking that threshold is harder than it sounds (see below).

Concept: a run report is an immutable event (ADR-0030)

A score only means something next to the configuration that produced it. So every report pins everything that could change the number: the embedding model, the query prefix, k, the dataset_version, and every Document's active Chunking Generation. It's then written once, to eval/runs/<UTC timestamp>-<model>.json, and never overwritten. A later run is a new file beside it.

That's your event-sourcing instinct applied to experiments. Each run is an appended event carrying its own context, history is never edited, and "how has retrieval changed?" becomes a fold over the files in runs/. The exclusive-create file mode open(path, "x") is the append-only guarantee. It fails atomically if the file exists, with no check-then-write race, much like an optimistic-concurrency check on an event stream's expected version.

Concept: one snapshot for the whole run

The report claims "these searches ran against these generations". To make that claim true even if someone reloads the store halfway through a run, all the queries run in a single REPEATABLE READ, read_only transaction. Every statement then sees one frozen snapshot of the database. It's the same reason you'd read an aggregate's version and its events in one transaction. The questions are embedded before the transaction opens, so slow model calls never hold it open.

The retriever is one SQL statement

SELECT chunks.document_id,
       chunks.locator,
       chunking_generations.chunking_strategy,
       1 - (chunk_embeddings.embedding <=> %(query)s::vector) AS similarity
FROM chunk_embeddings
JOIN chunks               ON chunks.id = chunk_embeddings.chunk_id
JOIN documents            ON documents.id = chunks.document_id
                         AND documents.active_chunking_generation_id = chunks.chunking_generation_id
JOIN chunking_generations ON chunking_generations.id = chunks.chunking_generation_id
WHERE chunk_embeddings.embedding_model = %(model)s
ORDER BY chunk_embeddings.embedding <=> %(query)s::vector, chunks.id
LIMIT %(k)s
  • The documents join restricts the search to each Document's active generation (ADR-0025). Chunks from an old chunking run stay in the database but are never candidates.
  • The chunking_generations join supplies each Chunk's chunking strategy, which the match rule needs to parse its locator. The spec said "joined to chunks/documents", but the strategy only lives on the generation, so this extra join is required.
  • chunks.id is a tie-breaker, so equal distances always come back in the same order and a re-run can't reshuffle ranks.
  • The question vector is sent as pgvector's text form '[0.1,0.2,…]' and cast with ::vector, using store/embed.py's helper. That helper was renamed from _vector_literal to vector_literal, because the leading underscore is Python's "private" convention and it now has a second caller.

Scoring a case, and the report

For each case, every retrieved Chunk is graded on its own with case_hit(gold, [chunk]), in rank order. The first hit's rank is what counts:

hit_ranks = []
for rank, chunk in enumerate(retrieved, start=1):
    if case_hit(gold, [chunk]):        # is *this* Chunk a gold hit?
        hit_ranks.append(rank)

if hit_ranks:                          # an empty list is falsy in Python
    hit_rank = hit_ranks[0]
else:
    hit_rank = None

Each entry in the report keeps the rank, the similarity at the hit (or, for unanswerable cases, the top-1 similarity), and the whole top-10 with scores. The spec only asked for the rank and similarity. Keeping the list means a miss can be investigated later without re-running anything, and gives the .NET retriever something to compare against result by result.

The test: hand-built vectors make ranking predictable

Concept: test a vector search with vectors you designed

Real embeddings are opaque, so you can't predict where a real question will land. The integration test therefore doesn't use them. It inserts fixture Chunks whose embeddings are basis vectors: a 1 in one of the 768 slots and 0 everywhere else. Basis vectors are at right angles to each other, so cosine similarity becomes plain arithmetic:

chunk 1.1       = basis(0)          query "rank one"   = basis(0)
chunk 1.2       = basis(1)            → 1.1 at similarity 1.0, everything else 0.0
heading chunk   = basis(2)
old-gen 2.1     = basis(3)          query "rank three" = 3·basis(0) + 2·basis(1) + 1·basis(2)
                                      → order 1.1, 1.2, heading (3 > 2 > 1)
                                      → heading's similarity = 1/√14

The embedding client is a fake that looks up the prepared vector for each (prefixed) question and records what it was sent. It's the same dependency-injection idea as handing an IEmbeddingClient stub to a .NET class under test. Python's Protocol just means the fake needs no shared base type. The test runs against the real Postgres in the isolated regdocs_test database, reusing store/tests' fixtures, so the SQL itself is what's being tested, including pgvector's actual <=>.

What the numbers say

Finding 1: the lexical/paraphrase gap is the headline

Every lexical question found its passage within the top 3, and 8 of 9 at rank 1. Paraphrase questions put the right Chunk first less than half the time, and 2 of 9 missed the top 10 entirely. Embeddings are supposed to be the tool that handles rewording, and they do help: some paraphrases hit at rank 1 with no shared key terms, such as q10 on outsourcing and q18 "ring me out of the blue". But this model still leans on shared words far more than on meaning. Exposing that is exactly why ADR-0029 reports the two separately.

One caveat: most paraphrase questions were written by Claude after reading the passage. If anything that makes them easier than questions from someone who hadn't seen it, so the real gap is probably at least this wide.

Finding 2: the misses are about vocabulary
CaseQuestion (paraphrase)What came back instead
q06insurers "that only cover risks for their own corporate parent"The right document (CP131), but the wrong clauses. The passage's key word is captive, and the question never says it.
q08whether candidates "have enough hours to do the job"CP160's "Levels of experience". Close in meaning, but the gold says time commitments.
q12"slow paying its annual bill for being regulated"Rank 4. The top 3 were CP54 consumer clauses about charges, and "levy" is the missing word.

In each case, the domain term a compliance analyst would use (captive, time commitment, levy) was the bridge the model couldn't cross from everyday language. That points at the usual next experiments: hybrid search (merging keyword and vector results) and query rewriting (having an LLM restate the question in the corpus's vocabulary before searching).

Finding 3: a similarity threshold can't separate "not covered" from "covered"

The two unanswerable questions scored a top-1 similarity of 0.727 and 0.705. Several correct hits scored lower: q18 was right at 0.652, q12 at 0.698, and q06's best (wrong) result was 0.696. Any cut-off that rejects both unanswerable questions would also reject answers that were correct. Similarity scores from one model aren't calibrated probabilities. They depend on topic and phrasing as much as on relevance. That's why "unanswerable" handling in real RAG systems usually happens later in the pipeline: the LLM is told to say "the documents don't cover this" when the Chunks it's given don't contain the answer. The harness records the scores (and deliberately applies no threshold, per the issue's Out of Scope) so that decision can be made with data.

Finding 4: supersession passed, but only just

Both supersession cases hit at rank 1, with the current CP54 clause first. In q17 (premium rebates), though, the superseded CP47 passage came second at 0.853, just behind CP54's 0.881. The old and new versions say almost the same thing, so they embed almost identically. Similarity alone has no idea which one is current. Only a small scoring margin put the right one first. The harness doesn't score where the superseded passage lands (not asked for, and ADR-0030's report fields don't include it). It's visible in the report's top-10 list, and it's a good candidate for a future metric, or for a retrieval rule that filters out superseded Documents altogether.

What /code-review caught

Two reviewers ran in parallel, one against the repo's standards (CLAUDE.md, ADRs, sibling code) and one against the spec (issue #32). The spec reviewer found no defects. Every acceptance criterion was met, apart from committing the baseline, which is waiting on you. Both flagged the same latent crash, and the standards reviewer found the rest.

Bug: an unembedded store would have scored a perfect-looking 0.0

Both reviewers noticed that an empty result list was handled "gracefully": top1_similarity became None and the case became a miss. Follow that through. If you ran the harness before store/embed.py, every search would return nothing, every case would miss, and you'd get a clean report saying Recall@10 = 0.00, pinned, timestamped and immutable. It would be a plausible-looking number caused by a setup mistake, which is exactly the silent failure ADR-0028 forbids. (The console table would actually have crashed on formatting None, but only after the report was already written.)

The fix changed the design from "tolerate empty" to "empty is impossible". _retrieve now raises RuntimeError: no nomic-embed-text Chunk Embeddings to search -- load the store and run store/embed.py first, so every later line can rely on at least one result. A new test runs the harness against an empty database and expects that error. It was red first.

Bug: a dataset of only unanswerable cases divided by zero

_metrics divides by the number of answerable cases. Unanswerable cases are filtered out before grouping, so no group can be empty, but overall can: a dataset of only unanswerable questions crashed with ZeroDivisionError. That can't happen with today's 20 cases, but the right response to "there's nothing to average" is a clear message, not a stack trace from arithmetic. It now raises ValueError: the dataset has no answerable cases, so recall and MRR are undefined. A test pins it, and it was also red first.

Smaller fixes
  • Every locator was parsed twice. The first version called case_hit on the whole list (to validate every locator), then again chunk by chunk (to find the rank). One pass now does both: grading every Chunk individually also validates it.
  • Speculative Generality: a k parameter nobody passed. run_eval(…, k=K) invited callers to vary something ADR-0030 wants pinned, and neither the tests nor the CLI used it. It's gone. K = 10 is the one source, and the report records it.
  • Comments for the densest Python. CLAUDE.md asks for line-by-line comments where the syntax is unfamiliar, and the review found gaps. There are now comments for f-string format specs (:<26, :>7.2f ≈ C#'s {x,-26}, {x,7:F2}), a nested f-string, dict(cur.fetchall()) (≈ ToDictionary), ensure_ascii=False, the chained comparison a == b == 10 (no C# equivalent), and next(…) (≈ First(predicate)).
  • A misleading fixture name. The fixture report returned a (report, client) tuple, while its comment claimed it "stashed the client on the report". It's now fixture_run, with an accurate comment.
  • A comment in store/embed.py had been reflowed badly by the rename.
Judgement calls left as they are

Dicts, not a RetrievedChunk dataclass. This was flagged as possible Primitive Obsession, since find_locator.py uses a @dataclass. But case_hit (#30) takes dicts, and the report is JSON. A type here would be converted back to a dict on both sides.

The sys.path edit appears twice, in run_eval.py (so the script runs) and in the test conftest.py (so the tests import store/tests' fixtures). That's the repo's existing pattern for sharing code between folders with separate virtualenvs. Making /store an installable package would remove both, but that's a bigger decision than this ticket.

The superseded passage's rank isn't scored (see Finding 4). That's out of the spec's scope, deliberately, but now there's evidence it's worth adding.

What's next

The baseline report goes in with this PR. From here, the harness is a regression suite for retrieval quality. The Week-2 .NET retriever has to reproduce these exact numbers on the same embeddings. If it scores lower, check the search_query: prefix, the distance operator (<=> is cosine, <-> would be Euclidean) and the active-generation join. After that, the findings above suggest the experiments worth running, each measured by a new report in eval/runs/: hybrid keyword + vector search (for the paraphrase gap), filtering out superseded Documents, and eventually a second embedding model side by side. chunk_embeddings is keyed by model for exactly that purpose (ADR-0024).
