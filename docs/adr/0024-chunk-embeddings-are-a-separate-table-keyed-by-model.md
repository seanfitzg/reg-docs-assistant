# Chunk Embeddings live in a separate table, keyed by (chunk_id, embedding_model)

`chunk_embeddings` is its own table — `chunk_id`, `embedding_model`, `embedding vector(N)`, `created_at` — primary keyed on `(chunk_id, embedding_model)`, not a plain `embedding` column added to `chunks`.

The obvious, tutorial-shape approach is a single `embedding` column on `chunks`, overwritten whenever a chunk is re-embedded. This project has already committed hard to the opposite pattern everywhere else a derived artifact can be redone with a different method: Chunking Generation keeps every past generation rather than overwriting `chunks`, and the loader's two `/code-review` rounds went specifically to enforce that nothing already written is silently rewritten. A plain column would reintroduce exactly that problem the first time a second embedding model gets tried — the old vectors would vanish, and any eval-harness comparison between two models' retrieval quality (an explicit portfolio-plan goal) would become impossible without a full re-embed. Keying by `(chunk_id, embedding_model)` instead of introducing a matching "Embedding Generation" entity (the Chunking Generation pattern's obvious extension) was a deliberate simplification: Chunking Generation earns its own table because a Document needs one "active" pointer to resolve an ambiguity; there's no equivalent ambiguity here, since retrieval always knows which model it's querying with and can join on model name directly.
