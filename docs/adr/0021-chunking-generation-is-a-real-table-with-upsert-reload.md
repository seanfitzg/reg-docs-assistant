# Chunking Generation is a real table in /store, loaded by upsert-only

`/store` persists Chunking Generation as its own table (`document_id`, `created_at`, strategy used), with `chunks.chunking_generation_id` as a proper foreign key — not just a bare string column copied from the JSON. The loader upserts every row by its deterministic id (from `ingestion/ids.py`) and never truncates or wipes the store before reloading.

In `/schema`'s JSON world, Chunking Generation is only ever an id referenced by `Chunk` and `Document` — there's no dedicated schema file for it. Carrying that same implicit shape into the relational store would mean the one place that could actually enforce the domain's own rules — a Document points at exactly one active Generation, earlier Generations are never deleted, only superseded — has no referential integrity backing those rules at all. A wipe-and-reload loader would be simpler to write, but directly violates "earlier generations stay in storage to satisfy Replay" (`CONTEXT.md`) the moment anything downstream (e.g. embeddings, added in a later migration) depends on a generation surviving between loader runs. Upsert-by-id is the only reload strategy consistent with Chunks and Generations being immutable once written.
