# /store's loader is Python-only, not duplicated in the .NET track

`store/loader.py` exists once, in Python, the same as `/ingestion`. Track A (.NET) is not getting its own copy that loads `ingestion/output` into `/store` independently.

This extends ADR-0012's reasoning rather than reopening it: ingestion is already a single shared pipeline because PDF parsing and chunking "aren't RAG, agent-orchestration, or model-integration work," so duplicating them across both tracks would teach nothing new about either stack while risking the two tracks silently loading different data. Getting already-ingested JSON into Postgres is the same kind of plumbing, for the same reason — it's not retrieval or model-integration work either, and the loader reads ingestion's output in ingestion's own shape (its manifest, its id-derivation convention from `ingestion/ids.py`, duplicated as one line rather than imported across venvs). A second, independently-written C# loader would have to re-derive and re-trust those same conventions from scratch, with nothing keeping the two in sync. This project's dual-stack portability proof lives in the shared event schema, shared corpus, and both tracks eventually *reading* from one populated store — not in re-implementing how that store gets populated.
